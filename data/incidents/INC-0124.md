# Postmortem: month-end reconciliation crowded out the API on ledger-service-02

Severity sev2. Night of 2026-01-31 into 2026-02-01, 23:35 to 03:10 UTC. Runbook used: RB-001. Authors: ledger squad.

## Impact

For most of the night, API requests on ledger-service-02 either queued for a database connection or gave up with a Hikari message that the request had timed out after 30000ms. The effect travelled upstream: payments-api received `503` from ledger-service while the pool was starved. The incident record opens with the page at 23:35 and closes at 03:10, which is when the reconciliation batch finished. The `503` responses themselves ended earlier, in the minutes after the fix described below.

## Who was where, and what they decided

The batch had begun at 23:30. Five minutes later `LEDGER-W210` fired. Month-end has a reputation, so the first assumption was a CPU problem, and the responder opened RB-001, the runbook for a ledger-service JVM running hot. CPU on the pod was elevated but not saturated, which did not match that story, and the investigation turned to the connection pool instead.

There the picture was plain. The pool of 20 stood at 20/20 and `hikaricp_connections_pending` climbed to about 40. The connections were held by `recon-worker-*` threads, and on ledger-db-01 the 20 matching sessions were sitting in long transactions. The batch had been started with `LEDGER_RECON_PARALLELISM=24`, a higher worker count than there are connections to give them.

The decision was to shrink the batch, not the traffic and not the pool. Parallelism went from 24 to 4 and the pod running the batch was restarted so that it would read the new value. Four workers left 16 of the 20 connections to requests. The job carried on, more slowly, until 03:10. The pool size was left as it was, in line with RB-001's advice not to enlarge it mid-incident.

## Why the end time is 03:10

Responders had no clean "recovered" moment to record for the batch itself: the customer-facing `503` ended in the minutes after the restart, but the work that caused the starvation was still running and only finished at 03:10. We therefore record the end as the batch's completion, with the earlier recovery noted here in prose.

## What we take from it

- Page on pending connections, not only on pool utilisation, so a starved pool is recognised before anyone opens the CPU graph.
- Compare batch settings with the pool size whenever either one changes; 24 workers against 20 connections should not have been allowed to start.
- Add the batch's worker count to the month-end checklist, so someone reads it before the run starts.

## Open items

The write-up does not cover how long a full reconciliation takes at four workers compared with the night it ran at 24, or whether four is the right permanent number. The ledger squad should measure that at the next month-end and report it alongside the chosen setting.
