## Notes

**The bad value.** Kafka parses `message.max.bytes` as an integer count of bytes. Whoever wrote the change wanted roughly ten megabytes and typed `message.max.bytes=10MB`; the parser refuses the suffix and the broker aborts during startup. Ten mebibytes written correctly is 10485760.

**Why the tool saw success.** systemd treats our broker unit as up the instant its process is spawned, so a restart returns 0 even when the JVM is about to abort on its configuration. In August the tool trusted that return code alone, paused for a fixed time and moved on; nothing asked whether a broker had actually rejoined the cluster. Two brokers were gone before a human was involved.

**Effect on each Kafka user.**

| Service | Effect |
|---|---|
| ledger-service | Published nothing for ten minutes and lost nothing. Its retry queue peaked around 1,200 entries and was empty by 10:28. CPU unchanged. |
| orders-api | Customers could check out the whole time. Order events go to the outbox first; publishing paused, resumed with a backlog of a couple of thousand events and cleared it in under a minute. |
| notification-worker | Idle: with no new messages arriving, it had nothing to fall behind on. |

No event was lost anywhere.

## Follow-ups

- team-platform: health-check each broker after its push, so a config run halts on the first broker that does not come back.
- Change review: byte-valued Kafka settings must be bare integers; add a lint for unit suffixes.
- On-call note: a halted run is never resumed as-is; the corrected file goes out as a fresh run.
