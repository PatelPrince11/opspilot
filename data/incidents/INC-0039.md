# 4 May 2025: auth-service-01 and the goroutines that stayed

sev3 · 12:35 to 21:25 UTC · runbook: RB-005 · host: auth-service-01

Between those two lines no other clock time was written down.

## Summary of the day

For 530 minutes, from 12:35 to 21:25, one authentication pod, auth-service-01, was killed by the kernel for going past its container memory limit. Kubernetes marked each kill `OOMKilled`. This was a memory leak, and it showed in two graphs that rose together: the pod's memory, and the count of goroutines inside the process. RB-005 is the runbook for killed pods and was the one that applied.

## What a rising goroutine count says

Goroutines are the unit of concurrent work in a Go service. Each one holds a stack and everything it references, and a goroutine that never returns keeps both alive. A count that only rises therefore means work is being started and never finishing, and memory grows in step with it until the container limit cuts the process off. That points at unfinished work and away from one oversized buffer, but it stops short of a cause: naming the code that started the goroutines needs a goroutine profile, and none was kept.

## Where the evidence ends

- No goroutine profile exists, so no code path is described here.
- No count of kills was written down.
- Only auth-service-01 is named; nothing is recorded about the service's other pod.
- What ended the kills is not in the record.

## Ownership and close

The on-call took the incident, and by 21:25 the kills had stopped.

## What to do differently

Capture a goroutine profile from the pod early in a climb, while its count is still high but the container has not yet been killed. After the next restart that evidence is gone.
