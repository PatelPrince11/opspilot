# Postmortem: feature-cache growth on fraud-scorer-01, 15 February 2025

Prepared by team-risk for the weekly review. Severity sev2. All times UTC. The incident ran from 08:50 to 10:50, a window of 120 minutes.

## Incident record

| Field | Value |
|---|---|
| Service at fault | fraud-scorer, pod fraud-scorer-01 |
| Who noticed it | payments-api, scoring with static rules instead of the model |
| Contributing system | redis-features-01, answering slowly |
| Codes seen | `FRD-W118` on the scorer, `PAYAPI-W0310` on payments |
| Runbooks consulted | RB-006 for the cache, RB-005 for the memory shape |

## Effect on payments

From 08:50 until the new pods took traffic, payments-api logged `PAYAPI-W0310`: each time a score did not come back in time, it decided with its static rule set instead of the model. Those rules are deliberately coarse. The fallback alert paged at 09:02, and the on-call opened the incident as sev2.

## Sequence of events

- 08:50 `FRD-W118` appears in fraud-scorer-01's logs; payments-api begins logging `PAYAPI-W0310` within that minute.
- 09:02 Page to the team-risk on-call from the payments fallback alert.
- 09:10 Grafana "Container memory (working set)": fraud-scorer-01 had been rising steadily since about 08:50. Pod status showed no restarts.
- 09:18 The on-call worked through RB-005's question of leak versus undersized limit. The previous day's graph was level, traffic this morning was ordinary, and the climb had no peak behind it. A steady rise with flat load points at growth inside the process, so the limit was not touched.
- 09:30 RB-006: `redis-cli --latency` against redis-features-01 returned figures far above its normal range.
- 09:45 The debug build's tracemalloc endpoint on one worker: the fastest-growing allocation site was in the feature cache.
- 10:05 Latency samples from redis-features-01 eased back to normal. `FRD-W118` stopped. Memory did not fall.
- 10:20 Rolling restart of the fraud-scorer Deployment.
- 10:40 New pods serving; working set at its usual baseline; no `PAYAPI-W0310` since the new pods took traffic.
- 10:50 Declared resolved after a quiet watch.

## Analysis

Two things had to be true at once. First, redis-features had to be slow. It is a single node with no failover, and RB-006 lists big key scans and BGSAVE as what usually slows it. This postmortem does not settle which of those, if either, was behind this morning's latency; that sits with the open actions. Second, the scorer had to keep holding what it fetched. The scorer's local feature cache is known to swell whenever the feature store lags, and it did in the fraud-scorer-01 worker traced at 09:45.

Gunicorn's own safety net did not cover it. Each worker is replaced after roughly 5000 requests (`--max-requests`, plus jitter), which caps how long any one worker lives, but the cache grew faster than workers were being replaced. Memory never reached the 3 GiB limit, so no pod was killed.

The scorer stayed up but slow, and payments-api did what it is built to do with a slow scorer. The visible symptom was therefore on the payments side, and the first twenty minutes went to finding which service was actually unwell.

## What worked, what did not

Worked: the payments fallback; RB-005's shape question, which kept us from raising the memory limit and hiding the growth; RB-006's latency check, which tied the growth to a slow store within minutes.

Did not work: nothing alerted on the scorer's own warning rate, and the cache gave nothing back after the store recovered, so a restart was still needed.

## Agreed actions (proposals, no owners assigned)

1. Alert on how often each pod logs `FRD-W118`, not only on the payments fallback.
2. Investigate why the feature cache does not shrink once fetches are fast again.
3. Find out what slowed redis-features this morning.
