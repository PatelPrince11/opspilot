# The 19 March 2025 zone push, question by question

sev2 · 15:15 to 15:50 UTC · cause internal-dns, seen in orders-api · runbooks: RB-020, RB-027

**What did we see?**

From 15:15 orders-api-02 could not always open new database connections. Each failure was a
lookup of the database hostname answered with NXDOMAIN: as far as that answer went, the name did
not exist. Some lookups still succeeded, so the errors came and went rather than holding steady.
Requests on connections opened before 15:15 kept working.

**What changed at 15:15?**

A change to the `prod.internal` zone file went out through the rollout tool, in a run scoped to
internal-dns-01 alone. It placed the new file there at 15:15 and restarted coredns. The new file
lacked the record orders-api uses for its database. The run touched no other host.

**Why intermittent?**

Pods don't ask internal-dns directly. The cluster CoreDNS sends each `prod.internal` query to one
of the two servers at random and keeps the reply for up to 30 seconds. Only internal-dns-01 served
the new file, so a cache period that happened to land there came back NXDOMAIN and one that went
to the other server came back with the address. orders-api-02 kept drawing both.

**Did the rollout tool notice anything?**

No. It finished with 0 failed hosts. Its only check was the exit status of
`systemctl restart coredns`, and that was 0. CoreDNS came up on internal-dns-01, loaded the zone
and served it. The zone just had one name fewer.

**Was this the "daemon that doesn't come back" case?**

We opened RB-027 because a config push started it. The danger RB-027 warns about is a process
that dies after systemd has already called the restart a success; its example is the `kafka`
unit, which is `Type=simple`, so systemd reports success the moment its process is spawned.
That did not fit. `systemctl is-active coredns` on internal-dns-01 returned active and it answered
an SOA query. The daemon was fine; the file it served was not.

**How did we pin it down?**

Paged at 15:26 on orders-api's connection errors. At 15:31, from a VM, we asked each server for
the name directly and compared SOA serials, as RB-020 lays out. internal-dns-01 had a newer serial
and answered NXDOMAIN; the server the run had not touched still had the older serial and returned
the record. A record that one copy of the zone has and the newer copy lacks points at the change
itself, and the diff of the 15:15 push showed the record removed.

**How was it fixed?**

The record went back into the zone source with a higher serial, and the corrected file went out
through the same tool to internal-dns-01 at 15:38, again with 0 failed hosts. Once the cluster
cache turned over, lookups from orders-api-02 resolved every time; the last failed one was logged
at 15:39. We watched until 15:50 and closed: 35 minutes from the first push.

**What should change?**

- Before a zone push: list the records the new file removes compared with the live one, and stop
  for a person to confirm each removal.
- After the push: ask the server for a handful of names that must always exist, rather than
  trusting the restart's exit code.
- An NXDOMAIN rate for `prod.internal` names seen by pods, so the page names DNS and not the
  database connection.
