# Ticket: CPX-W430 from a single card proxy during an egress node patch

| Field | Value |
|---|---|
| Severity | sev1 |
| Service | card-processor-proxy, with payments-api affected |
| Started | 2026-09-16 19:41 UTC |
| Resolved | 2026-09-16 20:23 UTC |
| Team | team-payments |
| Runbooks | RB-029 (limiter, placement, levers), RB-016 (checked; its retry lever not used) |

**Description.** Card payments failing with `PAYAPI-E1107` at roughly a quarter of the arrival
rate. card-processor-proxy-01 rejects attempts with `CPX-W430`; card-processor-proxy-02 is
absent from the logs.

## Comments

**19:38** · team-platform: the egress node hosting card-processor-proxy-02 is cordoned, then
emptied, ahead of a kernel update.

**19:40** · team-platform: card-processor-proxy-02 evicted. Its replacement is `Pending`.

**19:41** · first `CPX-W430` on card-processor-proxy-01; `PAYAPI-E1107` starts on payments-api.

**19:48** · payments on-call: paged on the `PAYAPI-E1107` rate.

**19:52** · payments on-call: pod listing for the proxy shows -01 Running and the replacement
Pending; the scheduler's event blames anti-affinity plus the egress taint. Only two nodes carry
that taint. One is cordoned and the second already hosts -01.

**19:55** · payments on-call: every rejection comes from card-processor-proxy-01. Processor
latency is normal and the processor is not answering with its own rate-limit reply. Nobody
outside is throttling us; our own limiter is.

**19:58** · payments on-call: the numbers. Payments come in at roughly 240 per second.
One instance gets 180 tokens a second (`CPX_LOCAL_RPS`), and every attempt spends one, retries
included. Each admitted attempt finishes a payment, so at most 180 payments a second get through
and the remaining 240 − 180 = 60 a second use up their attempts and fail. The dashboard shows
about 60 `PAYAPI-E1107` a second. With both instances up the budget is 2 × 180 = 360, well above
the arrivals.

**20:02** · payments on-call: read RB-016 because retries are in the picture. Its first move,
cutting payments-api's attempts per payment down to 1, would not help here. The limiter lets through 180 attempts a
second whatever the attempts per payment, so the same 60 a second would fail, only sooner, and the
processor is not the one pushing back. The attempt setting stays at 3.

**20:06** · payments on-call: RB-029's other lever is raising `CPX_LOCAL_RPS` on -01 to 360 for
as long as it is the only instance. That needs -01 restarted, and since the replacement is
already Pending, a rollout won't remove -01; we would have to delete it ourselves and serve
zero payments until it returned.
Trading a partial outage for a total one: no. We wait for the node.

**20:18** · team-platform: patch applied, node rebooted.

**20:20** · team-platform: node uncordoned.

**20:22** · card-processor-proxy-02 Running and taking traffic.

**20:23** · `CPX-W430` gone, `PAYAPI-E1107` back to its usual level. Resolving.

## Resolution note

Card payments failed at a sustained rate for 42 minutes. We chose to leave `CPX_LOCAL_RPS` and
the attempt setting as they were (see 20:02 and 20:06); the fix was the node coming back.

## For the review

- Cordoning either egress machine is a payments event. Proposal: maintenance on the egress pool
  is announced to team-payments first and done off-peak.
- Open question: should the patch have waited for a quieter hour?
- An alert for `CPX-W430` coming from one instance only, which says an instance is missing, would
  have named the cause at 19:41 instead of at 19:55.
- Pooling the token budget between the two instances is still only a proposal. With it, -01
  alone could have used the full 360.
