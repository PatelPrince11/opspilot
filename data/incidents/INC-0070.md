# Ticket: kafka-02 /var full, GC logs in /var/log/kafka

**Opened:** 2025-08-12 02:30 UTC
**Severity:** sev3
**Host:** kafka-02.prod.internal
**Runbook:** RB-008
**State:** closed 03:45 UTC

## Description

The alert for `/var` usage on kafka-02 fired at 02:30. On this VM `/var` lives on the root disk, so a full `/var` puts every process that writes to the root filesystem at risk, and the first visible sign was `ENOSPC` on writes under `/var`. The word "Kafka" in a disk ticket tends to make people think about topic data, so for the record: the alert is about `/var`, not the data directory `/data/kafka`.

Rotated the GC logs in `/var/log/kafka` and cleared the rotated copies that were not needed. `/var` dropped quickly.

**03:30**

**03:45**
Usage is holding, so I am closing the ticket. The cause is the GC logs in `/var/log/kafka`; why they were allowed to reach this size is still to be looked at.

## Resolution

Rotated the broker GC logs on kafka-02, which freed enough space on `/var`. Only `/var/log/kafka` was worked on; the data volume played no part in this.

## Why this was rated sev3

The alert and the failed writes were both on the root disk of one broker, and the part of the broker that holds Kafka's messages was not what had run out of room. The risk was that other writers on the same root filesystem would start failing too. The runbook's instruction for this host is short: rotate the GC logs and leave the data directory out of it, and that is what was done.

## What ENOSPC meant here

`ENOSPC` says a write had nowhere to go on the filesystem it was aimed at. It does not say which filesystem. On a broker there are two candidates, the data volume and the root disk, and the first job is to find out which is full. Here it was the root disk, because the GC logs live there.

## Follow-ups

- Look at the logrotate setup for `/var/log/kafka` on kafka-02 and decide whether the logs were meant to be rotated and were not.
- Check the same directory on the other two brokers while at it.
- If a rotation file turns out to be missing, put it in config management so a rebuilt host gets it back. This is a conditional follow-up: nothing has confirmed that it is missing.
