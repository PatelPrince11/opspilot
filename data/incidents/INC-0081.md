# Postmortem: the missing database record, 19 September 2025

Authors: team-platform. Severity: sev2. Timestamps are UTC. Window: 20:25 to 21:40, 75 minutes. Runbooks cited: RB-020, RB-027.

## Summary

A zone-file push on the evening of 19 September 2025 left internal-dns-02 serving a version of `prod.internal` missing the record catalog-api-02 needs for its database. The other internal-dns server's copy of the zone still carried it. Whether a lookup worked therefore depended on which server the cluster resolver asked, and catalog-api-02 saw failures that came and went for 75 minutes. The tool finished reporting 0 failed hosts, so the push raised no alarm by itself.

## Impact

The symptom surfaced in catalog-api rather than in internal-dns. Each time catalog-api-02 wanted its database address and got `NXDOMAIN`, that attempt failed; a later attempt might reach the other server and work. The result was an uneven error pattern on one instance, easy to mistake for a database fault. No request count was recorded for the window.

## Why it came and went

Pods ask the cluster CoreDNS, which forwards `prod.internal` queries to one internal-dns server picked at random and caches the reply, `NXDOMAIN` included, for no more than 30 seconds (`cache 30`).

For catalog-api-02 that produced a series of short windows. A window opened by a query to the intact server carried the address. A window opened by a query to internal-dns-02 carried `NXDOMAIN` for up to half a minute. Both servers were up; one of them simply held less.

## Why the push looked fine

In September 2025 the tool's only verdict on a host was whether `systemctl restart` succeeded. Nothing in that sequence compared the records a server held against the records it should hold. CoreDNS restarted, read the file and served it, with the record missing. Nothing flagged it.

RB-027, the runbook for VM config pushes, was an obvious first read. It is about services that exit soon after systemd reports a start, and it names the `kafka` unit as `Type=simple` to make the point. Nothing suggested coredns had exited; the open question was what internal-dns-02 served.

## How it was narrowed down

- The errors in catalog-api-02 shared one cause: the name query for the database host was answered `NXDOMAIN`. Failures alternated with successes, which suggested the two servers disagreed, not that the name was gone everywhere.
- RB-020 reads intermittent pod failures as two servers disagreeing, and its test is to question each server directly and compare answers and SOA serials.
- The push that landed at 20:25 fitted the start of the errors.

Why the pushed file lacked the record was not recorded.

## Resolution

team-platform took the incident, and the lookups stopped failing by 21:40. Which step ended the failures was not recorded. RB-020 has a remedy for a missing record; whether it was applied is not recorded.

## Lessons

1. A clean exit from the tool says the process restarted. It says nothing about which names the server can answer.
2. Random forwarding across two servers makes a one-server fault look flaky from inside the cluster, which slows the recognition of a disagreement.
3. RB-027 helped to rule out a daemon fault; the content question sat with RB-020.

## Proposed follow-ups

- Give catalog-api's connection errors the failing name and the resolver's answer, so the next page points at DNS instead of the database.
- Have the push summary show, for each server, the SOA serial and how many records it now holds.
