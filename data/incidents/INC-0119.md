# Ticket: 504s only when a request lands on edge-gateway-03

**Component:** edge-gateway-03.prod.internal · **Priority:** sev3 · **Span:** 21:25 to 22:25 UTC on 2026-01-16 (60 minutes) · **Playbook:** RB-014

## Symptom

Requests handled by edge-gateway-03 ended in a `504` from 21:25. Requests that the load balancer gave to the other edge pods were answered as usual, so which pod a caller reached decided the outcome. With three pods sharing the traffic, only the share landing on this one met the slow path.

## What kind of problem this is

A problem that follows a pod is a different problem from one that follows a service. The route timeout at the edge is 15 s, so a `504` here is a request that outlived that limit, and the useful question is why it did so on this pod and not on its two siblings. Had the cause been one slow service, callers of that route would have failed on all three pods. Had it been the gateway software or the node pool as a whole, the other pods would be expected to show it as well. A single affected pod with healthy siblings narrows the suspects to what is specific to that pod: the process, or the machine beneath it.

For callers the difference is practical. A retry can land on a healthy pod, so the symptom looks random from outside even though it is tied to one place, which is also why a ticket for this naming the pod is more useful than one naming a route. That is why the ticket names the pod and not a route.

## Notes from the thread

**platform on-call:** the failures follow one pod, whatever it forwards. If an upstream service were slow, its route would fail on all three edge pods. So the pod, or the machine under it, comes before any service team.

**platform on-call:** the other two pods reach the same services without trouble. RB-014 sends latency that comes from the gateway or from the node pool to team-platform, which fits the shape here although only one pod is involved.

**platform on-call:** the node under edge-gateway-03 is under resource pressure, and the gateway pod running on it is slowed by that. No figure was recorded, and the node is not named.

## Ownership and outcome

team-platform owns this, so the ticket stays with them. They took the node problem, and the `504`s had stopped by 22:25, when the ticket was closed. What was done to the node is not recorded. This ticket records no change to an upstream service or to a route, and no count of failed requests.

Pressure on the node is the only explanation on file for the slowdown on this one pod, and no measurement of that pressure is recorded either.

Follow-ups: record in the ticket which node carries the gateway pod when it is first suspected, and check the pressure on the host node as soon as a single edge pod looks slow while its siblings look fine, so the comparison with the other two pods is made early.
