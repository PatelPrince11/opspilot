# Ticket: catalog-db-01 /var at 100%, log agent failing

**Opened:** 2025-01-02 21:25 UTC by DBA on-call
**Severity:** sev3
**Host:** catalog-db-01.prod.internal
**Runbook:** RB-008
**State:** closed

## Description

Log agent errors from catalog-db-01 started arriving at 21:25 over the network: `ENOSPC` each time it tried to save its read position. Nothing local is being written. Postgres still serving. Taking it.

## Comments

**21:31, DBA on-call**
Free space check on the mount: 100% used. `/var` shares the root disk on this VM, so anything that writes to the root filesystem is at risk, not only logs. Checked the database first: a read from `psql` returns normally and the catalog-api error rate is flat. Treating this as sev3, no page to the catalog-api on-call yet.

**21:38, DBA on-call**
Sized the directories under it with `du`, sorted. Top entry by a wide margin is `/var/log/journal`. Postgres's own directories are small next to it. No `.gz` pile-up, apt cache tiny.

**21:44, DBA on-call**
`journalctl --disk-usage` agrees: the journal alone accounts for nearly all of the used space. Looked at `/etc/systemd/journald.conf`: every line is still commented out, the file is the distribution default. No `SystemMaxUse` anywhere in it.

**21:52, DBA on-call**
Holding off on deleting anything by hand inside `/var/log/journal`. The runbook path for this case is a vacuum through journald itself. Ran `sudo journalctl --vacuum-size=500M`. It removed archived journal files oldest first and left the active ones.

**21:58, DBA on-call**
`df -h /var` now has plenty of headroom. Log agent resumed: its position writes succeed and it began shipping what it had buffered.

**22:02, DBA on-call**
Before calling the space problem solved, checked for deleted files still held open by a process: `lsof +L1` came back empty. So the journal was the whole story, not one piece of it.

**22:10, DBA on-call**
Making the fix permanent on this host. Added `SystemMaxUse=500M` under `[Journal]` in `/etc/systemd/journald.conf` and restarted `systemd-journald`. `journalctl --disk-usage` after restart is under the cap. This VM did not have the cap before tonight; it does now.

**22:25, DBA on-call**
Checked whether anything failed while the disk was full. Postgres did not log write errors for its data during the window that we can find, and catalog-api showed no change. The only casualties we can name are the log agent's position file and whatever local log lines could not be stored before the vacuum.

**22:40, DBA on-call**
Watching growth. `journalctl --disk-usage` steady. Root disk usage steady.

**23:15, DBA on-call**
Agent backlog fully shipped, usage flat for over half an hour. Closing, 110 minutes after the first error. Open questions below.

## What a reader should know

- The vacuum only removed archived journal files. Recent entries, including everything from tonight after 21:52, are still on the host.
- Local log lines from the first part of the evening may be missing; the agent's buffer covered what it could, but anything written straight to disk while it was full did not survive.
- Postgres was not restarted and nothing in its directories was touched.

## Follow-up

Tonight the first sign came from the log agent complaining about its own position file, over the network. Proposal: alert on that specific agent error, since it fires even when nothing local can be written.
