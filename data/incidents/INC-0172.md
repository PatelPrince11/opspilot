## Takeaways from the captain

The tell was timing. CPU moved on both pods at the minute the rollout completed, while the worker count, the limit and the request had not changed. That rules out the usual throttling cause, a worker count that follows the node, because ours has been pinned since May.

Rolling back was chosen over raising the limit. Either would likely have stopped the throttling, but a bigger limit would have hidden whatever the release does differently, and we would have shipped that cost.

Open before the release goes out again:

- Profile one worker on the new build against the old one under the same load, and find where the extra CPU goes.
- Add a CPU and throttling comparison to the release checklist, a few minutes after each rollout.
- Ask whether the release needs a bigger limit for a good reason. If it does, raise it on purpose, separately from the release.
