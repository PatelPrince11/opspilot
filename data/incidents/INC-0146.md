# Campaign traffic overran the search cluster, 2026-04-15

search timeline, sev3, 11:05 to 11:45 UTC (40 minutes). Runbook: RB-030.

```
11:05  first SRCH-E502 on search-api-02; the queues of search-cluster-02 and
       -03 are full and both nodes are refusing queries
....   team-catalog works the incident (clock times of its steps were not kept)
11:45  no more SRCH-E502 from search-api-02
```

## Where the load came from

A growth campaign pushed people toward search. The volume exceeded what search-cluster could absorb: each node holds only so many waiting queries in its search pool, and with that queue full it declines the next arrival. search-api-02 handed that decline to its caller as `SRCH-E502`. The campaign's rate in requests per second was not measured, so the size of the overshoot was never worked out.

## The edge in this incident

The edge limit on `/search` (250 per pod, the subject of RB-030) was not what turned searches away. The searches got past the edge, arrived at search-api-02 and were declined by the cluster behind it, which is why the error is a search code and why the symptoms name a pair of cluster nodes instead of the gateway. A higher edge number would likely have sent more queries toward nodes whose queues were already full.

## Reading the timeline

Only the first and last entries carry clock times. The first is the first `SRCH-E502` seen on search-api-02, which marks the moment the cluster pools began refusing; the last is the point from which the code no longer appeared. Between them, 40 minutes passed with the pools of search-cluster-02 and search-cluster-03 full.

## Impact

The incident is sev3 and ran from 11:05 to 11:45. For forty minutes a search routed through search-api-02 could end in an error rather than a result list, because the node that received the query had no room left to queue it. The share of searches that failed and the campaign send time were not recorded.
