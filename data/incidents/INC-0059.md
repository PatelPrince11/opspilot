# Wednesday 9 July 2025: checkout slowed by a new filter with no index

This was a sev3 for the inventory team, open from 10:40 until 15:30 UTC: 290 minutes.

**The effect.** Checkout was where it hurt. Stock reservations were timing out, so inventory-service-01 and inventory-service-02 both logged `INV-E220`, and orders-api-01, orders-api-02 and orders-api-03 passed the failure up as `ORD-5003`. The database underneath, inventory-db-01, looked busy rather than idle.

**The cause.** That morning's release changed the reservation query so that it filtered on `expires_at`. The column had no index. Postgres therefore answered every reservation by scanning the whole `reservations` table, one row after another, and that was the work keeping inventory-db-01 busy. The inventory pools hold 20 connections per pod, 2 x 20 = 40 in all, and with every query taking longer, those connections stayed occupied and callers queued up to their timeout.

**How we knew.** Two things carried most of the weight. The errors were on both inventory pods at the same moment and the database was working hard, which together pointed at a query and away from one sick pod. After that, the slow statement's plan showed a sequential scan on `reservations` with a filter on `expires_at`, which matched what the release had added. The procedure is in RB-015; I won't repeat it here.

**The fix.** We built the missing index, `reservations_expires_at_idx`, with `CREATE INDEX CONCURRENTLY`, so that reservations and other writes could carry on while it was built. This was chosen over backing out the release. The build and the recovery both fell in the afternoon, and the incident was closed at 15:30.

**Who was affected.** Anyone checking out during the window could hit the failure. The effect travelled in a chain: the database was slow, inventory-service timed out on its reservation, and orders-api reported the failed call on checkout. Each hop logged its own code, which is why the same incident left three different traces in three services.

**Since then.** The table now has the index and the reservation filter runs against it. When a release adds a filter on a column, the question to ask at review is whether an index covers that column in the table the query reads.
