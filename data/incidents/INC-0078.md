# Refused feature-store writes on 9 September 2025: questions and answers

Risk and platform, sev3, 11:20 to 13:05 UTC. RB-019 was the reference.

**What did we see first?**

At 11:20 both fraud-scorer-01 and fraud-scorer-02 started logging `FRD-E140`. Behind it, redis-features-01 was turning down writes with `MISCONF`, so the per-card counters fraud-scorer maintains stopped moving.

**What does `FRD-E140` mean for the business?**

fraud-scorer increments a velocity counter, with an expiry, on every score it computes. While the writes were refused those counters could not be updated, so they went stale and stayed that way until writes recovered. Scores computed in between were working from counters that were out of date, which is why the code is worth watching even when the service looks otherwise healthy.

**Memory looked fine. Why did the node refuse writes anyway?**

Redis held about 14 GB on a 32 GB VM, comfortably inside its own limits. The refusals came from a different place: the node's snapshot attempts were failing, and Redis stops accepting writes when that happens. The Redis log carried `Can't save in background: fork: Cannot allocate memory`.

**Why would a fork fail on a machine with that much free memory?**

A hardening change from team-platform had switched redis-features-01 to strict memory accounting (`vm.overcommit_memory = 2`, ratio 80). With no swap, that caps total commitments at 32 GB x 80% + 0 = 25.6 GB. A snapshot forks a child that is billed about like its parent, so 14 GB plus 14 GB asks for roughly 28 GB, more than 25.6 GB. The machine had room; the accounting rule did not.

**How did it end?**

The setting went back to 1, a new snapshot was started by hand and finished, and writes were accepted again. The `FRD-E140` lines from both scorers stopped, and we closed at 13:05. Almost two hours passed between first symptom and fix, since the cause sat in the OS settings rather than in anything Redis reported about memory.

**What changes afterwards?**

The sysctl on the host was a patch. The hardening baseline that applied strict mode has to stop doing so, otherwise it can come back. That is with team-platform.

**What is still open?**

Whether other hosts picked up the same baseline value has not been looked at.
