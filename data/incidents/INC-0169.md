# Ticket: fraud-scorer writes failing against redis-features-01

**Opened:** 2026-06-17 11:35 UTC
**Severity:** sev2
**Hosts:** redis-features-01.prod.internal, fraud-scorer-01.prod.internal, fraud-scorer-02.prod.internal
**Runbook:** RB-019
**State:** closed, 13:20 UTC

## Description

Starting at 11:35 each scorer pod logged `FRD-E140`, the code for a velocity-counter write that did not go through. Each rejected write came back from redis-features-01 as `OOM command not allowed`. The failing operation was the write; the ticket records no other symptom on the node.

## Comments

**No time kept, on-call**
Both pods failed together. They share one datastore, a single Redis node with no failover partner, so redis-features-01 is the place the ticket points at.

**No time kept, on-call**
Used memory on redis-features-01 had reached its configured `maxmemory` of 24gb, and the node runs with `noeviction`. Redis picks no keys to drop under that policy and returns the error above to every further write. RB-019 is the runbook for this node.

**No time kept, team-platform**
Took over the node. The steps team-platform took on the node were not written into this ticket.

**13:20, team-platform**
Writes are accepted, and neither pod logs the code any more. Closing.

## What the scorers lose

A velocity counter is a running per-card figure that fraud-scorer updates with an increment each time it scores a payment, and each counter carries an expiry. While the node refused writes, the figures the scorers would have updated stayed where they were. A counter is only as useful as its latest increment, so the refusals mean stale inputs for as long as they last, and the size of the staleness grows with the time the node stays full.

## Duration and effect

The ticket stayed open for 105 minutes, counted from its opening to the closing comment. Across that span the velocity counters could not be refreshed. fraud-scorer increments a counter for a card on every score and gives it a time-to-live, so each refused write left a counter at its last value while real activity went on. The longer the node stayed full, the further those counters fell behind.

## The machine

redis-features-01 is a 32 GB virtual machine with no swap, and Redis on it is limited to 24gb of that. That leaves 32 - 24 = 8 GB of the machine outside the Redis limit. fraud-scorer is the only client named in this ticket, and its two pods are the ones that logged the code.

## Ownership

redis-features belongs to team-platform, which also owns RB-019, so the handover to team-platform in the comments above kept the incident with the owners of the datastore. The scorer pods belong to the fraud-scoring side; their logs carry the code, and the ticket was opened at 11:35.
