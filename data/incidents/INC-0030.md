## Why the board runs in this order

The on-call worked the two runbooks in sequence instead of guessing. RB-006 went first because it is the cheaper check: one look at the memory panel, one latency check against the feature store, one search of the scorer logs. All three came back clean by 01:21, and that closed the memory branch for good. Only then did the modest average CPU become interesting, and RB-002 turned that oddity into an answer within a few minutes.

The start-up log made the count plain without exec'ing into the pod. With `WEB_CONCURRENCY` unset, gunicorn takes the visible CPU count, which on a 16-core node is 16. That many busy workers can drain a smaller CPU allowance early in a period.

## Lever chosen

At 01:44 the on-call raised the CPU limit, the quicker of RB-002's two fixes. The CPU request was not edited, so scheduling had no reason to move the pod.
