# The cache that was there but not ready

Early on Sunday 26 October 2025 I was carrying the catalog pager. What follows is my account of a short sev3, which began at 02:50 UTC and had ended by 03:10.

The alert that reached me was about catalog-api, not Redis. catalog-api-02.prod.internal had begun emitting `CAT-E301`, our code for "couldn't get this from the cache, fetching it from catalog-db instead". In my experience that code had always meant an unreachable Redis box, so I opened RB-017 already picturing a dead VM and a failover.

That picture was wrong. I found no timeouts and no refused connections. Each failed cache lookup from catalog-api-02 came back from redis-cache-02.prod.internal with one word: `LOADING`. So Redis was alive, listening and replying; its reply simply said it was still pulling its dataset off disk and couldn't hand out keys yet. That only happens shortly after a Redis process starts, so redis-cache-02 had restarted. Why it restarted, I don't know, and this account doesn't speculate.

Which left me one real responsibility. When cached product data is unavailable, the thing at risk is the database behind it, since nearly all catalog reads are normally answered by Redis and every miss becomes a SQL query. Following the checklist, I kept two graphs open side by side: catalog-db CPU and the rate of `CAT-E301`. Database work went up, as you'd expect, yet it never got near the threshold at which RB-017 asks for escalation. Running out of sessions was never a concern either, because catalog-api's connection pools are bounded.

I left Redis alone. A process in the middle of loading is minutes away from healthy, and restarting it would only reset that clock. The checklist also rules out manual promotion, and nothing here tempted me toward it.

Shortly before 03:00 the `LOADING` answers ceased. catalog-api-02's lookups started succeeding, and `CAT-E301` went quiet. Redis came back with little useful content, so catalog-db kept absorbing extra reads for a while as popular products were cached again. That warm-up behaved just as the runbook predicts: hits rose, database CPU eased back to normal, and at 03:10 nothing looked unusual anymore. Twenty minutes, first error to finish.

What I'm keeping from this:

- `CAT-E301` says the cache didn't deliver. It doesn't say the cache host is gone. Had I read the wrapped Redis error before anything else, I'd have skipped some pointless checks.
- With a cache that's reloading, the job is to wait and keep watching the database. That's the core of RB-017's catalog-db section in practice.
- What triggered the restart of redis-cache-02 remains unknown.
