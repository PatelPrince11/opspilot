# ledger-service-02 OOMKilled on 21 April 2025: questions and answers

ledger squad, sev3, 18:05 to 22:30 UTC. We worked from RB-005 and RB-001.

**What happened?**

ledger-service-02 was restarted by Kubernetes, and the pod's last state read `OOMKilled` (exit code 137). The container had passed its memory limit and the kernel ended the process without warning. The incident ran from 18:05 to 22:30.

**Was it the limit or the service?**

The working-set panel showed memory climbing steadily on ledger-service-02 before the kill, which is the pattern RB-005 associates with a leak. A limit that was merely too small would have shown flat memory until a peak. We therefore did not treat a larger limit as the answer.

**Why is a JVM involved at all?**

ledger-service is a Java 17 process, PID 1 in its container, with its heap set by `-XX:MaxRAMPercentage=75`. A heap that keeps expanding walks the whole container towards its limit. The collector's log is `/var/log/ledger/gc.log`, and that is where the history of collections can be read.

**How did it end?**

The replacement pod came up and ran normally; we closed at 22:30. A leak ticket was opened, and its heap summary was taken from the new process as its memory grew again, because the first one's heap went when it was killed.

**Which two documents did we use, and for what?**

RB-005 is the team-platform FAQ on killed pods. It supplied the question we asked first: does memory rise steadily or sit flat until a peak? RB-001 is the ledger-service runbook for the JVM, and it supplied the garbage-collection and heap context for what a growing heap looks like.

**What did the kill do to the evidence?**

A killed process takes its heap with it, so anything we learned about what had grown had to come from the restarted process after it climbed again. That limits how much the ticket can say about the original run.

**What is the ticket still expected to answer?**

The ticket owns the question of what grew. This write-up does not name an object type or a code path, and no heap-dump finding is claimed.

**What changes?**

- Follow the leak ticket to find the source of the growth.
- Revisit the memory limit only if kills return.
