# Handoff: one DNS server missing a name, 2026-03-24

**internal-dns-01 and internal-dns-02, with inventory-service-01 and inventory-service-02 affected. sev3, resolved. 13:30 to 14:15 UTC. Runbook: RB-020.**

What you need to know: a config push delivered a new `prod.internal` zone file that has no entry for the inventory database. It arrived on internal-dns-02 and on no other server. internal-dns-01 still holds the previous file, which has the entry. Asked about that one name, the two servers disagree.

Impact: from 13:30 inventory-service-01 and inventory-service-02 began reporting `no such host` for their database name, and the failures were intermittent, not constant. 0 VMs showed any lookup problem; they put internal-dns-01 first in their resolver list and take an NXDOMAIN as the end of the matter, so they follow whatever internal-dns-01 says. The pods go through the cluster's resolver, which caches answers briefly, so a miss from internal-dns-02 was followed by a hit once the cache had turned over.

How it went:

- 13:30 · errors start in the inventory pods. Same name each time.
- 13:40 · the datastore VMs checked and clean, so the problem was on the pod side of the path and not in the database itself.
- 13:47 · looked at the zone file on disk at each server. internal-dns-01 has the inventory database line. internal-dns-02 does not, and its copy is the newer of the two.
- 13:52 · restored the line in the zone source and pushed the corrected file to internal-dns-01.
- 13:58 · same file on internal-dns-02. Both servers now agree.
- 14:15 · no new `no such host` lines from the inventory pods. Closed.

Not known: why the new file reached only internal-dns-02, and whether the push dropped anything besides the inventory database name. I only checked that one name.

For day shift:

1. Find out why the push stopped at one server, from the rollout run's own record.
2. Ask the owner of the zone source whether a line vanishing from a zone file can be flagged before a push goes out.
3. If a pod still errors after both servers agree, give the cluster cache a moment before restarting anything.
