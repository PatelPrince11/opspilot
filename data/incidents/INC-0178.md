# Two logout waves from one auth-service release

team-identity · sev2 · 2026-07-21, 14:05 to 14:30 UTC · runbooks: RB-026, RB-018

## What users went through

Twice in one afternoon signed-in users were sent back to the login page. The first wave came
from sessions created before the release, the second from sessions created while the release was
serving. Signing in again worked both times.

## What the release changed

This release altered how auth-service serializes session values kept in redis-sessions, keys
beginning `sess:`. Code from the release couldn't decode a value written by the previous build,
and the previous build couldn't decode one written by the release. When a value won't decode,
the lookup fails like any missing session would: `AUTH-E401X`, and the user goes to sign in.

We roll auth-service with stock Deployment settings, adding a pod before removing one. So for
several minutes both builds served traffic, and users whose requests hopped between builds were
signed out.

## Timeline (UTC)

- 14:05 rollout starts.
- 14:08 first pod of the release Ready. `AUTH-E401X` climbs immediately.
- 14:11 auth-service-01 and auth-service-02 both run the release. Sessions from before it can
  no longer be read.
- 14:14 paged on the `AUTH-E401X` rate.
- 14:16 Redis ruled out first, using RB-018's checks: same sessions primary as this morning, and
  auth-service had logged no failed session writes. No failover.
- 14:17 RB-026: errors started as that first pod went Ready, and this release touched stored
  session data, which is where rolling back stops being free.
- 14:20 rolled back with `kubectl rollout undo`.
- 14:23 a pod on the previous build is serving again. Users who signed in during the release
  start failing.
- 14:30 that second wave has faded; resolved.

## Why one release made two waves

Each wave was sessions written by one build meeting a reader from the other. Moving forward
stranded sessions created before 14:08. Moving back stranded those created between 14:08 and the
rollback. Rolling back didn't end anything; it changed which group of users paid.

## What was kept

The session values stayed in redis-sessions, unreadable rather than deleted: neither build could
interpret the other's. What users paid was forced sign-ins.

## Was rolling back right?

At 14:20 it felt safe. It wasn't cheaper. RB-026 asks, whenever a release changes stored data,
whether older code understands what newer code wrote. Here it did not. Had we stayed put and
shipped a build that decodes both encodings, people who signed in after 14:08 would have kept
their sessions. That build shipped one day later, 2026-07-22.

## Changes we are making

1. Release review flags any change to persisted formats: session values, cache keys, message
   bodies. Such changes ship in two steps: first a reader for both formats, later the new writer.
2. A dashboard panel splitting `AUTH-E401X` by ReplicaSet, so a glance shows whether errors sit
   on one build.
