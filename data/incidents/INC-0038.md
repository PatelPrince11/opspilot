# Ticket: ledger-service-01 loses its database address now and then

**Service:** ledger-service (pod ledger-service-01.prod.internal) · **Sev:** sev3 · **Date:** 2025-05-02
**Window:** 06:30 to 07:45 UTC · **Also involved:** internal-dns-01.prod.internal · **Refs:** RB-020, RB-027

## What was observed

From 06:30 ledger-service-01 logged refusals when it tried to take a fresh database connection. Every error is about a name that could not be turned into an address, and the DNS status in it is `NXDOMAIN`. Between the refusals the same pod managed to connect. The pattern held for 75 minutes, 06:30 to 07:45, with this pod the only one named.

## Effect on the service

Anything in ledger-service-01 that needed a new database connection while a bad answer was cached had to fail, because the name of the database was reported as non-existent for that stretch. The next refresh of the resolver cache could go the other way, which is why the service seemed to recover and relapse without any change on the pod. The ledger database is not suspected: the error is raised before any connection to it is attempted.

## Thread

**ledger on-call:** the message is about the name of the ledger database, not about waiting for a free connection, so this is not a ledger problem. Passing it to platform.

**platform on-call:** a zone-file push to internal-dns-01 went out just before 06:30, and the tool summarised it as 0 failed hosts. `prod.internal` lookups from a pod pass through the cluster resolver, which hands each one to either internal-dns machine and remembers the answer for up to 30 s. With two machines holding different zones, answers arrive alternately right and wrong.

**platform on-call:** A push was involved, so RB-027 got a look. It covers units that look started and then fail, and uses `kafka` (stated as `Type=simple`) for illustration. `coredns` showed no sign of having stopped, so the useful question became the contents of internal-dns-01's zone file. That belongs to RB-020, which suggests querying both servers for the same name and putting their serials side by side.

**platform on-call:** the file on internal-dns-01 lacked the ledger database record. Quiet from 07:45, and the ticket was closed at that point with the work handed to the platform team.

## Why the zone and not the pod

Two facts point away from ledger-service-01 itself. The message names a failed lookup, which happens before the database is contacted, and the failures began at the minute a zone-file push reached internal-dns-01. An application fault would not line up with a DNS push, and a database fault would not produce a DNS status in the error text.

## Handoff

Ownership: team-platform. Why the record was absent from the pushed file, and what brought the errors to an end, were not recorded. RB-020 carries a remedy for this class of fault; whether it was used is unknown. Failed attempts were not counted, so the size of the impact is unknown.

Idea for later: when a zone push reaches only one internal-dns machine, look at the other one's answer for a service-critical name before the run is called finished.
