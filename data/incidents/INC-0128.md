**Description.** The pod behind catalog-api-02 keeps restarting. Each restart shows `OOMKilled`. The restarts come at a steady interval of about 50 minutes, not in a cluster, and the Deployment recovers each time by itself. The restarts began with the start of the window at 09:00, and the last one in the log sample came at 14:50; the ticket tracks the cause rather than each individual restart, which is why the comments below are about the pattern.

## Comments

**10:10** · catalog on-call: the pod's restart count has climbed through the morning. Its last terminated state reads `OOMKilled`, exit code 137, so the container went past its memory limit each time, rather than being stopped for some other reason. RB-005 covers the triage for this reason.

**11:00** · catalog on-call: the memory graph for catalog-api-02 since 09:00 is a straight climb, drops at each restart, and climbs again, with the restarts spaced about 50 minutes apart. The two restarts so far, at 09:50 and 10:40, are exactly that gap apart. A graph that is a straight climb is not a flat line with a peak.

**11:20** · catalog on-call: raising the limit is not the move. It would stretch the climb and push the same kill later. The limit stays as configured.

**12:15** · catalog on-call: found what grows. catalog-api keeps a cache of responses, keyed by the full query string, and there is no cap on entries. Each distinct query string becomes its own entry.

**15:20** · catalog on-call: no OOMKill since the one at 14:50. Resolving. For the record, 09:00 to 15:20 is 380 minutes; at one kill per 50 minutes that is 380 / 50 = 7.6, so about 7 restarts of this pod in the window.

## Restart pattern in the log sample

The log sample for the window shows seven kills, at 09:50, 10:40, 11:30, 12:20, 13:10, 14:00 and 14:50. Each is 50 minutes after the one before, and the first is 50 minutes after 09:00. A further one would have been due at 15:40, after the resolution. Between kills the cache entry count in the same log climbs and then starts again from small, which matches the in-process cache being lost with each restart.

## Impact

The record for this ticket covers the restarts of catalog-api-02 and nothing else. We are not describing customer-facing effects, because none were gathered.
