# RISK ticket: fraud-scorer-02 memory keeps rising

**Opened:** 22 July 2025, 08:15 UTC, by the team-risk on-call
**Severity:** sev3
**Component:** fraud-scorer
**Hosts in scope:** fraud-scorer-02.prod.internal, redis-features-01.prod.internal
**Reference:** RB-006
**State:** Resolved 11:00 UTC

## Description

The routine memory review this morning put fraud-scorer-02 at the top of `kubectl top pod` for the scorer, well above its sibling and higher each time the command was repeated. No restarts, no kills so far. Raising a ticket rather than paging, since nothing customer-facing is broken yet. A few `PAYAPI-W0310` lines have shown up on the payments side.

## Comments

**08:31, on-call.** The odd part is the gap between the two pods, so starting there. Counted `FRD-W118` per pod over the last stretch of logs: fraud-scorer-02 has several times as many as its sibling. Both pods read from the same feature store, so whatever is slow is hitting -02 harder.

**08:44, on-call.** `py-spy dump` on two workers of fraud-scorer-02 (the debug image has `SYS_PTRACE`). Most threads sit in the feature client waiting for a reply. They are not busy; they are queued.

**09:02, on-call.** `redis-cli --latency` against redis-features-01: mostly low samples, broken up by regular spikes far above normal. That is the slow read the warnings complain about.

**09:20, on-call.** Lined up the memory panel against the `FRD-W118` counts for fraud-scorer-02. Every bump in warnings is followed by a step up in working set, and the steps never come back down. The sibling, with far fewer warnings, has barely moved. RB-006's known pattern, seen from the outside.

**09:41, team-risk lead.** Holding the restart for now. While the store is still spiking, new pods would just start filling up again. Let's see if the spikes settle.

**10:05, on-call.** Per RB-006, a slow feature store usually means a heavy key scan or a BGSAVE on it. It is a single node with no replica to take reads, so anything heavy on it reaches every feature fetch. Asked team-platform to look at the store's side.

**10:20, on-call.** Latency samples on redis-features-01 back at their usual floor. `FRD-W118` on fraud-scorer-02 is down to zero.

**10:24, on-call.** Working set on fraud-scorer-02 is flat but not falling. Gunicorn replaces a worker after `--max-requests 5000` (with `--max-requests-jitter 500`), so memory would come back only as workers cycle out. Taking the RB-006 restart instead of waiting on that.

**10:30, on-call.** `rollout restart` on the fraud-scorer Deployment issued.

**10:44, on-call.** New pods up. fraud-scorer-02 now level with its sibling. No new `PAYAPI-W0310` since the restart finished.

**11:00, on-call.** Quiet. Resolving.

## Closing notes

- The memory review caught this before anything paged. Comparing the two pods side by side was the quickest lead.
- Holding the restart until the store settled meant one restart was enough.
- fraud-scorer-02 took many more slow reads than its sibling, and its memory tracked those warnings step for step. Why one pod was hit harder is open.

## Open questions

1. Why did fraud-scorer-02 see so many more slow reads than the other pod from the same store?
2. Should the memory review flag a gap between the two scorer pods, not only an absolute level?
3. Is a 5000-request recycle short enough for a cache that grows in steps like this?
