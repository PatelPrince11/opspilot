# Worked example: the migration that waited (15 May 2025)

A replay written by the catalog squad. The migration itself was harmless. What hurt was everything that lined up behind it.

## The setup that afternoon

- catalog-api (namespace `catalog`; catalog-api-01 and -02 in logs) serves requests with async workers. Each pod's SQLAlchemy pool allows 10 connections plus 5 overflow, so at most 30 sessions on catalog-db-01.prod.internal.
- redis-cache served about 95% of product reads. That afternoon catalog-api handled roughly 1,200 product reads a second, about 60 of which missed the cache and went to catalog-db. On top of that came about 5 writes a second (price and stock edits) to `products`.
- Schema changes ship as Alembic migrations, run by the pre-deploy Job `catalog-api-migrate`. The Deployment rolls only if the Job succeeds.
- A weekly export reads all of `products` to rebuild the search index, inside one transaction of about 40 minutes.
- **There was no `lock_timeout` on migrations then.** It dates from 2025-05-16, the day after. A migration waiting for a lock would wait as long as it took.

## Minute by minute

**13:30.** The weekly export begins. Its open transaction holds an `ACCESS SHARE` lock on `products` until it ends. Ordinary reads and writes don't conflict with that.

**14:02:00.** The release's migration runs `ALTER TABLE products ADD COLUMN discontinued_at timestamptz;`. Adding a nullable column with no default is quick, but it needs an `ACCESS EXCLUSIVE` lock, if only for an instant, and that conflicts with the export's lock. The ALTER waits.

> *What it meant:* a lock request that conflicts with one already *waiting* queues behind it, even when it would be compatible with the lock actually held. From here on, every new `SELECT` or `UPDATE` on `products` waited behind the ALTER, which waited behind the export.

**14:02:00 to about 14:02:00.5.** Cache misses and writes reached catalog-db at about 65 a second, and each one stuck while holding its pool connection. At that rate, 30 connections were gone in under half a second.

> *What the graphs showed afterwards:* the pool graph jumped from a handful in use to 30 between two scrapes.

**14:02:15.** First `504`s at the edge, for requests stuck since 14:02:00 that reached the 15-second route timeout. Requests answered from the cache kept succeeding, so most product pages still loaded.

**14:02:30.** catalog-api started logging

```
QueuePool limit of size 10 overflow 5 reached, connection timed out, timeout 30.00
```

for requests that had waited 30 seconds for a connection. The edge had already given up on those at 15 seconds, so clients only ever saw `504`.

**14:06.** The edge alert on the `504` rate paged the catalog on-call.

> *What it meant:* about 5% of product reads and every product write were failing while catalog-db looked idle.

**14:07.** catalog-db-01: CPU low, no `CAT-E301` from catalog-api, 32 sessions in use out of 97 usable. Not load, not slots.

**14:08.** Who waits on whom:

```sql
SELECT pid, usename, wait_event_type, wait_event,
       pg_blocking_pids(pid) AS blocked_by,
       now() - query_start AS waiting,
       left(query, 60) AS stmt
FROM pg_stat_activity
WHERE datname = current_database() AND state <> 'idle'
ORDER BY xact_start;
```

First row: the export, active. Second: the ALTER, `wait_event_type = Lock`, `wait_event = relation`, blocked by the export's pid. Then 30 `catalog_app` sessions, each blocked by the ALTER's pid.

**14:09.** Cancelled the migration, not the export:

```sql
SELECT pg_cancel_backend(<pid of the ALTER>);
```

The queue emptied at once, connections came back, and the `504`s stopped within the minute. The Job failed, so the Deployment never rolled and the new code wasn't serving yet.

> *Why the ALTER and not the export:* cancelling the export also clears the queue, but it throws away 40 minutes of work, and the ALTER had to be retried anyway.

**14:10.** The export finished by itself.

**14:40.** Migration rerun with a lock timeout. The column was added in milliseconds.

## What changed

Since 2025-05-16 the migration Job runs with `PGOPTIONS='-c lock_timeout=5s'`. A migration that can't get its lock within 5 seconds fails instead of building a queue, and the Job retries it a few times after a pause. Five seconds of queued requests is a blip; seven minutes was an incident.

Before a release that includes a migration, the squad now also checks for long transactions on the target table, and doesn't release during the weekly export.

## What the on-call does in one

1. Find the waiting DDL (`wait_event_type = 'Lock'`, a statement starting `ALTER`, `DROP`, or `CREATE INDEX` without `CONCURRENTLY`) and what blocks it.
2. Cancel the DDL with `pg_cancel_backend`. The queue clears immediately.
3. Confirm the deploy didn't carry on without its migration.
4. Rerun the migration with `lock_timeout` once the long transaction has finished.
