# Kafka: broker data disk filling up

Streaming on-call (team-platform). Three brokers: kafka-01.prod.internal, kafka-02.prod.internal, kafka-03.prod.internal, broker ids 1, 2 and 3. Each has one data directory, `/data/kafka`, on its own volume. Topics are replicated 3 ways with `min.insync.replicas=2`.

The tools below live in `/opt/kafka/bin` on each broker. Run them from any broker.

## Procedure

1. **Confirm which broker and which volume.** On each broker, run `df -h /data/kafka`. Disks usually fill together because data is replicated. One broker much fuller than the others suggests a partition imbalance, not a retention problem.

2. **Find the biggest topics.**

   ```
   kafka-log-dirs.sh --bootstrap-server kafka-01.prod.internal:9092 --describe --broker-list 1,2,3
   ```

   The output is JSON with a size per partition. Sum it per topic. Over the last year, `ledger.entries` and `notifications.outbound` have been the top two every time.

3. **Check the topic's current retention.**

   ```
   kafka-configs.sh --bootstrap-server kafka-01.prod.internal:9092 --entity-type topics --entity-name notifications.outbound --describe
   ```

   If no override is listed, the topic uses the broker default, `log.retention.hours=168` (7 days).

4. **Check consumers before you shorten anything.**

   ```
   kafka-consumer-groups.sh --bootstrap-server kafka-01.prod.internal:9092 --describe --group notification-worker
   ```

   Note the largest `LAG`. If notification-worker is far behind (it logs `NTF-E710` when lag passes its threshold), shortening retention below its lag **deletes messages it has not read yet**. Get the owning team's OK first.

5. **Lower retention on the topic.**

   ```
   kafka-configs.sh --bootstrap-server kafka-01.prod.internal:9092 --entity-type topics --entity-name notifications.outbound --alter --add-config retention.ms=86400000
   ```

   That is 24 hours. The change applies without a restart.

6. **Wait for cleanup.** The broker checks retention every 5 minutes by default, removes eligible segments, and deletes the files about a minute later. Watch `df -h /data/kafka` fall over the next 10 to 15 minutes.

7. **Restore retention afterwards** once disk is expanded or the backlog is gone:

   ```
   kafka-configs.sh --bootstrap-server kafka-01.prod.internal:9092 --entity-type topics --entity-name notifications.outbound --alter --delete-config retention.ms
   ```

## If a broker already hit ENOSPC

With a single data directory, a broker that cannot write to it shuts itself down. Producers that need all in-sync replicas start failing when a second broker is affected. ledger-service logs `LEDGER-E455` for each entry it could not publish; those are queued for retry, so they are not lost, but the retry queue grows. Free space on the stopped broker (expand the volume; do not delete segment files) and start it again with `sudo systemctl start kafka`. It catches up from the other replicas.

## Gotchas

- **Retention only removes closed segments.** The active segment of each partition is never deleted, however old. A low-traffic partition can keep data well past `retention.ms` until its segment rolls (`segment.ms`, `segment.bytes`).
- **Compacted topics ignore this.** For topics with `cleanup.policy=compact`, `retention.ms` doesn't bound size the same way. Check `cleanup.policy` in the `--describe` output before relying on step 5.
- **Never delete files under `/data/kafka` by hand.** The broker's index and offset bookkeeping won't match the files, and the broker can fail to start.
- **`retention.bytes` is per partition**, not per topic. A topic with 12 partitions and `retention.bytes=10GB` can hold up to 120 GB on each replica.
- **ledger.entries has a 14-day retention for audit reasons.** Do not shorten it without finance ops' sign-off; expand the disk instead.
