# Worked example: the January 2026 month-end pool exhaustion

This is a walkthrough of a real night on call, written by the ledger squad so the next person can follow the same trail faster. The commands are the ones we ran. The lessons are at the end.

## The page

Just before midnight on 31 January 2026, `LEDGER-W210` started firing for ledger-service-02.prod.internal: HikariCP active connections above 90% of the pool. Our pool is `maximumPoolSize` 20, so that meant 18 or more in use. Ten minutes later payments-api began getting `503` from ledger-service. ledger-service-02's own log filled with:

```
java.sql.SQLTransientConnectionException: HikariPool-1 - Connection is not available, request timed out after 30000ms.
```

`connectionTimeout` is the HikariCP default, 30 seconds. Each of those lines is a request thread that waited half a minute for a connection, never got one, and failed.

ledger-service-01.prod.internal looked fine the whole time.

## What we checked first, and why it misled us

The month-end reconciliation batch had started on ledger-service-02 at 23:30. Everyone knows that batch is CPU-heavy, so the first guess was a CPU incident. CPU on that pod was clearly elevated, around two thirds of its limit, but it never got close to the limit. `top -H` showed the top CPU thread was an `http-nio-*` thread in Jackson serializer frames (the reconciliation result being serialized), with nothing spinning. The `recon-worker-*` threads, as we found later, were the ones holding the connections. Elevated, not saturated: that was the first hint the CPU was a bystander.

The deciding signal was the pool metrics in Grafana:

- `hikaricp_connections_active` flat at 20, the full pool
- `hikaricp_connections_pending` climbing from 0 to about 40 threads waiting for a connection

A thread dump agreed:

```
kubectl -n payments exec <ledger-service-02 pod> -- jcmd 1 Thread.print > month-end.txt
grep -c 'HikariPool.getConnection' month-end.txt
grep -B2 -A12 'recon-worker' month-end.txt | less
```

Dozens of `http-nio-*` threads sat in `HikariPool.getConnection`. Every one of the 20 connections was held by a thread named `recon-worker-*`.

## On ledger-db

Next we looked at what those 20 sessions were doing on ledger-db-01.prod.internal:

```sql
SELECT pid, client_addr, state,
       now() - xact_start AS in_tx_for,
       left(query, 70) AS last_stmt
FROM pg_stat_activity
WHERE usename = 'ledger_app'
ORDER BY xact_start NULLS LAST
LIMIT 25;
```

Twenty sessions from ledger-service-02's pod address, each inside a transaction that was already minutes old. They flipped between `active` and `idle in transaction`: read a page of accounts, compute, write adjustments, read the next page, all in one transaction. Our `leakDetectionThreshold` is 60000 ms, and the log confirmed it: a `Connection leak detection triggered for … on thread recon-worker-…` warning for each worker, about a minute after each chunk started. They weren't really leaks. Each connection was held deliberately for the length of a chunk.

The cause, put together: the reconciliation code wraps each chunk of accounts in a single transaction, and a chunk took about four minutes. The batch's parallelism was `LEDGER_RECON_PARALLELISM=24`, more workers than the pool has connections. The workers took all 20 connections and kept them, and normal API traffic on that instance had nothing left.

## What we did

1. Took the thread dump and the `pg_stat_activity` output first, as evidence.
2. Set `LEDGER_RECON_PARALLELISM=4` in the ledger-service ConfigMap.
3. Restarted the pod running the batch: `kubectl -n payments delete pod <ledger-service-02 pod>`. The reconciliation resumed from its last committed chunk with four workers, which left 16 connections for API traffic.
4. Watched `hikaricp_connections_pending` drop to 0 and the `503`s stop within a couple of minutes. The batch finished around 03:10, slower but without further trouble.

We did not raise `maximumPoolSize`. A bigger pool would have let the batch hold even more of ledger-db.

## Next time, faster

- When `LEDGER-W210` fires at month-end, look at `hikaricp_connections_pending` and the `getConnection` stacks before the CPU graph. Pending above zero with the CPU short of its limit means connections, not CPU.
- Count which thread names hold connections. If it's the batch, throttle the batch; don't touch the pool.
- `LEDGER_RECON_PARALLELISM` now defaults to 4.
- Proposed, not done yet: give reconciliation its own small pool so it can never take the API's connections, and commit per page instead of per chunk.
