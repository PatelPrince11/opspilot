# ledger-service: JVM high CPU

Owner: team-payments (ledger squad). Applies to ledger-service on Java 17 with HikariCP in front of ledger-db.

## Background

ledger-service is a Spring Boot application that writes double-entry records to ledger-db and publishes each committed entry to the `ledger.entries` Kafka topic. It runs as the `ledger-service` Deployment in the `payments` namespace. Log lines carry the instance names ledger-service-01.prod.internal and ledger-service-02.prod.internal.

When ledger-service burns CPU, the first alert is rarely a CPU alert. More often it is `LEDGER-W210` (HikariCP active connections above 90% of the pool), followed by `503` responses to payments-api. This ordering misleads people into treating it as a database problem. The connection pool fills *because* request threads are slow: each thread holds its connection for longer while it competes for CPU, so the same request rate needs more connections at once. Raising `maximumPoolSize` in that state only pushes more concurrent work onto an already saturated JVM and onto ledger-db.

There are three causes we have seen often enough to name:

1. **GC thrashing.** The old generation is close to full, the collector runs back to back, and almost no application work gets done. CPU is high, throughput is low, and latency is erratic. Usually a symptom of a heap that is too small for the working set, or of a leak.
2. **A hot loop in application code.** The best-known case is the Kafka retry path: when a publish fails, the entry is queued for retry and `LEDGER-E455` is logged. Before release 4.12 the retry worker had no backoff, so a broker outage turned into several threads spinning on the retry queue.
3. **Expensive serialization.** Very large batch reconciliation payloads (month-end) spend most of their time in JSON encoding. This shows up as high CPU on one instance only, the one that picked up the batch.

The investigation below separates these three. Capture evidence before you restart anything: a restart fixes the symptom and destroys the thread dumps you need for the follow-up.

## Investigation

### 1. Confirm it is CPU and not throttling

```
kubectl -n payments top pod -l app=ledger-service
```

If usage sits right at the container limit, check throttling first (see the container CPU throttling runbook). If usage is well above what the instance normally uses and below the limit, carry on.

### 2. Find the busy threads

Open a shell in the affected pod. The JVM is PID 1 in our images.

```
kubectl -n payments exec -it <pod> -- top -H -p 1 -b -n 1 | head -30
```

Note the thread IDs (the `PID` column in thread mode) with the highest CPU. Convert each to hex:

```
printf '%x\n' 4127
```

### 3. Take thread dumps

```
kubectl -n payments exec <pod> -- jcmd 1 Thread.print > ledger-threads-1.txt
sleep 10
kubectl -n payments exec <pod> -- jcmd 1 Thread.print > ledger-threads-2.txt
```

Search each dump for `nid=0x<hex>` to match the busy threads to stack traces. Two dumps ten seconds apart tell you whether a thread is stuck in one place or just busy.

What the stacks usually mean:

- Threads named `GC Thread#N` or `G1 Conc#N` at the top: go to step 4.
- Several `ledger-retry-*` threads inside the retry queue's poll loop: the Kafka retry spin. Check for `LEDGER-E455` in the logs and check broker health.
- One `http-nio-*` thread deep in Jackson serializer frames: an oversized reconciliation batch.
- Many threads `TIMED_WAITING` in `HikariPool.getConnection`: those threads are waiting, not burning CPU. They explain the `LEDGER-W210` warnings, not the CPU.

### 4. Check the garbage collector

```
kubectl -n payments exec <pod> -- jstat -gcutil 1 1000 10
```

Read the `O` column (old generation, % used) and `FGC`/`FGCT` (full GC count and time). An old gen pinned above 95% with `FGC` climbing every sample means the JVM is thrashing. Get a summary of the heap:

```
kubectl -n payments exec <pod> -- jcmd 1 GC.heap_info
```

GC logging is already enabled through `-Xlog:gc*:file=/var/log/ledger/gc.log`; pull that file if you need a timeline.

### 5. Look at the database side only after the above

If the JVM looks healthy and HikariCP still reports `Connection is not available, request timed out after 30000ms`, the problem is downstream: slow queries on ledger-db-01 or a lock queue. That is not a CPU incident; switch to the database runbooks.

## Remediation

- **GC thrashing:** restart the affected pod after taking a heap summary (`kubectl -n payments delete pod <pod>`; the Deployment replaces it). If it recurs within hours, raise the memory limit and keep `-XX:MaxRAMPercentage=75` so the heap grows with it. Open a leak ticket with the heap summary attached.
- **Retry spin:** fix the Kafka side first. Once the brokers accept writes again, the retry queue drains on its own. If CPU stays high after the brokers recover, restart the pods one at a time with `kubectl -n payments rollout restart deploy/ledger-service`.
- **Oversized batch:** let it finish if the other instance is serving traffic normally. If both instances are affected, pause the reconciliation job and tell finance ops.
- **Do not** raise HikariCP `maximumPoolSize` during the incident. It does not reduce CPU and it adds load to ledger-db.

## Verification

- CPU per pod back to its usual level in `kubectl top`.
- `LEDGER-W210` warnings stop within a few minutes.
- payments-api error rate for ledger calls returns to baseline and its `503`s stop.

## Appendix: reading a thread dump line

```
"ledger-retry-3" #48 daemon prio=5 os_prio=0 cpu=81234.12ms elapsed=5402.33s tid=0x00007f3a2c0b1800 nid=0x101f runnable
```

`nid` is the native thread ID in hex; it matches the hex value from `top -H`. `cpu=` is the thread's total CPU time, which is useful for comparing two dumps.
