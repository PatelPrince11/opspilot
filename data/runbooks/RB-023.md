card-processor-proxy (Go, namespace `payments`; card-processor-proxy-01.prod.internal and -02 in logs) presents a client certificate to the card processor on every connection. The processor issued it, not our CA. One-year validity; Secret `card-processor-client-tls`; read only at process start.

Looks like: `CPX-E600` on both pods from one exact minute, every call failing fast, payments-api logging `PAYAPI-E1107` once its 3 attempts are spent. No slowdown beforehand, no rate-limit codes.

```
$ k() { kubectl -n payments "$@"; }

# 1. every call, both pods?  (sample below is from the 2025-01-14 night: off-peak, about 3.5 failures/s per pod)
$ k logs -l app=card-processor-proxy --prefix --tail=-1 --since=10m | grep CPX-E600 | awk '{print $1}' | sort | uniq -c
   2071 [pod/card-processor-proxy-7d9f…-a]
   2056 [pod/card-processor-proxy-7d9f…-b]

# 2. what the processor sent back (alert wording depends on the processor)
$ k logs -l app=card-processor-proxy --tail=50 | grep CPX-E600 | tail -1
… CPX-E600 handshake failed: remote error: tls: expired certificate

# 3. dates on the certificate we present
$ k get secret card-processor-client-tls -o jsonpath='{.data.tls\.crt}' | base64 -d \
    | openssl x509 -noout -subject -issuer -enddate
subject=CN = <our merchant id>
issuer=CN = <processor CA>
notAfter=Jan 14 00:00:00 2025 GMT

# If the proxy log shows   x509: certificate has expired or is not yet valid
# then the proxy rejected the PROCESSOR's certificate. Nothing to rotate here: call the processor.

# 4. new key and CSR; the key never goes in the ticket
$ openssl req -new -newkey rsa:2048 -nodes -keyout client.key -out client.csr -subj "/CN=<our merchant id>"
# upload client.csr in the processor's merchant portal (up to 3 business days; their emergency line is faster)

# 5. check what came back before loading it
$ openssl x509 -in client.crt -noout -issuer -enddate
$ diff <(openssl x509 -in client.crt -noout -pubkey) <(openssl pkey -in client.key -pubout) && echo key matches

# 6. replace the Secret, then restart: the proxy only reads it at start.
#    The Deployment rolls one instance at a time (maxSurge 0, maxUnavailable 1), so while it rolls
#    one proxy carries everything and the egress budget is halved (180 instead of 360 per second).
#    Off-peak, or expect CPX-W430 for the minute or two it takes.
$ k create secret tls card-processor-client-tls --cert=client.crt --key=client.key --dry-run=client -o yaml | k apply -f -
$ k rollout restart deploy/card-processor-proxy && k rollout status deploy/card-processor-proxy

# 7. done when this stays at 0 and PAYAPI-E1107 is back to its baseline
$ k logs -l app=card-processor-proxy --prefix --tail=-1 --since=2m | grep -c CPX-E600
0
```
