# orders-api heap leak checklist

For when orders-api memory climbs steadily and pods restart every few hours. Work top to bottom and tick as you go. Namespace: `commerce`.

## Is it really a leak?

- [ ] Memory graph per pod is a sawtooth that climbs for hours, then drops at a restart. A flat line that jumps once is a traffic spike, not a leak.
- [ ] Restarts show one of two endings:
  - the container log ends with a V8 heap failure (V8 hit `--max-old-space-size`), in one of two wordings:
    - `FATAL ERROR: Reached heap limit Allocation failed - JavaScript heap out of memory`
    - `FATAL ERROR: Ineffective mark-compacts near heap limit Allocation failed - JavaScript heap out of memory`, usually after a run of long `Mark-Compact` lines from the GC, or
  - `kubectl -n commerce describe pod <pod>` shows `OOMKilled`, exit code `137` (the container limit was hit first)
- [ ] If you see `137` and never the V8 message, the heap flag is set higher than the container allows. Our standard is `--max-old-space-size` at about 75% of the memory limit. Check `NODE_OPTIONS` in the Deployment.

## Don't get misled by ORD-5003

- [ ] orders-api logs `ORD-5003` (checkout failed, downstream unavailable) when its calls to payments-api time out. Near the heap limit, long GC pauses freeze the event loop, so those calls time out on the orders-api side even when payments-api is fine.
- [ ] Before you page team-payments, check that payments-api latency is normal. If it is, the problem is in orders-api.

## Capture a heap snapshot (before restarting)

- [ ] Warning: writing a snapshot needs a lot of extra memory on top of the heap itself. A pod already close to its memory limit can be OOMKilled mid-snapshot, and you lose the pod and the file. Snapshot a pod whose memory is still well below its limit (under about 60%), earlier in the climb.
- [ ] orders-api starts with `--heapsnapshot-signal=SIGUSR2`. Pick a pod that is clearly growing but not yet near the limit; orders-api-02.prod.internal and orders-api-03.prod.internal usually lead.
- [ ] `kubectl -n commerce exec <pod> -- kill -USR2 1`
- [ ] Wait until the file stops growing. The process pauses while it writes, so traffic to that pod stalls for a few seconds.
- [ ] `kubectl -n commerce exec <pod> -- ls -la /app/*.heapsnapshot`
- [ ] `kubectl -n commerce cp <pod>:/app/<file>.heapsnapshot ./orders-heap.heapsnapshot`
- [ ] If you can, take a second snapshot 20 minutes later. Comparing two snapshots shows what's growing.
- [ ] If restarts happen too fast to catch by hand, a one-off rollout with `--heapsnapshot-near-heap-limit=1` added to `NODE_OPTIONS` writes a snapshot automatically as the heap nears its limit. The same OOM risk applies, so give that rollout a higher memory limit than the heap flag needs, and remove the flag afterwards.

## Mitigate

- [ ] `kubectl -n commerce rollout restart deploy/orders-api` buys hours, not a fix.
- [ ] Check what changed: a leak that starts right after a deploy points at that release. Roll back if the timing matches.

## Hand-off

- [ ] Attach the snapshots to the ticket. Open them in Chrome DevTools, Memory tab, "Comparison" view.
- [ ] Usual culprits we've found: listeners added per request and never removed, a module-level `Map` used as a cache with no eviction, and promises held by a retry helper.
