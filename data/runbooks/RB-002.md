If a service's p99 latency climbs while its CPU graph looks comfortable, suspect CFS throttling before anything else. We see this a few times a quarter, usually on payments-api or fraud-scorer, and it almost always gets misread as a downstream problem because the dashboards that people check first say the pods are only half busy.

Here is what is going on. A Kubernetes CPU limit becomes a CFS quota: the container may use its limit's worth of CPU time in each 100 ms period, and once it has spent that budget it is paused until the next period starts. A pod with a limit of 2 CPUs gets 200 ms of CPU time per 100 ms period. A process with 16 busy threads can burn that in about 12.5 ms and then sit frozen for the remaining 87.5 ms of the period. Real load is bursty: a burst of requests exhausts the quota in some periods, while other periods are nearly idle. Say 30% of periods hit the quota and the rest average about 20% of it. The minute average then works out to roughly 45% of the limit (0.3 × 100% + 0.7 × 20%), which looks comfortable, yet almost a third of all periods were throttled. Each request that lands in a frozen stretch waits for the next period, so the tail latency goes up while the average barely moves.

The check takes a minute. In Grafana, open the "Container CPU" panel and switch it to throttling: it plots `container_cpu_cfs_throttled_periods_total` divided by `container_cpu_cfs_periods_total`. Anything above roughly 25% of periods during the incident is a strong sign. To check from inside the container, run `kubectl -n payments exec <pod> -- cat /sys/fs/cgroup/cpu.stat` and compare `nr_throttled` with `nr_periods`. Our nodes run cgroup v2, so the file is at the cgroup root inside the container. Run it twice a few seconds apart and look at how much `throttled_usec` grows.

The usual trigger is a thread count sized to the node instead of the container. Go before 1.25 sets GOMAXPROCS to the node's core count, not the container limit, so a payments-api pod on a 32-core node schedules work as if it owned 32 cores. payments-api pins this with `GOMAXPROCS` set from the limit in the Deployment, but check it was not dropped in a refactor. fraud-scorer is the Python equivalent: gunicorn's worker count comes from `WEB_CONCURRENCY`, and if that is unset our entrypoint falls back to the CPU count it can see.

Downstream, the symptoms look like this. The edge returns `504` for payment routes once payments-api handlers exceed the gateway timeout. When fraud-scorer is the throttled one, payments-api logs `PAYAPI-W0310` because the score did not come back in time and it fell back to the static rules. In the incident from March, payments-api-03.prod.internal was logging W0310 at about 40 per second while fraud-scorer-01.prod.internal showed 30% throttled periods and only 45% average CPU.

To fix it now, raise the CPU limit for the affected Deployment (we keep requests unchanged so scheduling does not shift), or set the thread or worker count to match the limit and roll the pods. Do not just add replicas: if each new pod has the same mismatch, you get more throttled pods. Afterwards, add a throttling alert for the service if it does not have one, and record what changed in the incident ticket.
