# payments-db: WAL is filling the data disk

**Maintainer:** team-dba
**Scope:** payments-db-01.prod.internal (primary) and payments-db-02.prod.internal (streaming replica), PostgreSQL 16 on VMs. Data directory `/var/lib/postgresql/16/main` on its own 500 GB volume, mounted at `/var/lib/postgresql`. Tables and indexes take about 380 GB of it, normal WAL about 15 GB, and the ballast file 10 GB, which leaves about 95 GB free on a normal day.

> **Never delete files in `pg_wal` by hand.** Not with `rm`, not with `find -delete`, not with `pg_archivecleanup`. Removing a WAL segment the server still needs can make the primary unrecoverable without a restore from backup. Every path in this runbook frees WAL by fixing whatever is holding it, then letting Postgres remove it at the next checkpoint.

## Why this happens

PostgreSQL writes every change to the write-ahead log before it touches table files. Normally old WAL segments are recycled or removed at each checkpoint once nothing needs them. "Something still needs them" covers three cases on our setup:

1. **A replication slot is not advancing.** A slot guarantees that WAL is kept until its consumer confirms it. payments-db-02 streams through the physical slot `payments_db_02`. The `cdc_payments` logical slot feeds change data to the ledger reconciliation pipeline. If either consumer stops (replica down, CDC connector paused, network partition), the primary keeps every segment from the slot's `restart_lsn` onward. `max_slot_wal_keep_size` is set to 200 GB (see Prevention), but that cap is larger than the roughly 95 GB of free space on the volume. **A stuck slot fills the disk long before the cap invalidates it.** On this volume, the cap does not protect the disk.
2. **Archiving is failing.** With `archive_mode = on`, a segment cannot be removed until `archive_command` has succeeded for it. Our archive command uploads to object storage. If credentials expire or the bucket is unreachable, segments pile up in `pg_wal` and `pg_wal/archive_status` fills with `.ready` files.
3. **Write volume far above normal.** A bulk backfill or a runaway batch can generate WAL faster than checkpoints remove it. This is the least common cause and usually resolves on its own once the job ends.

Cases 1 and 2 account for every WAL disk incident on payments-db in the last two years.

## What you see

- Disk alert on payments-db-01 for `/var/lib/postgresql` above 85%, then 95%.
- If it reaches 100%, Postgres cannot write WAL and the primary stops:

  ```
  PANIC:  could not write to file "pg_wal/xlogtemp.31877": No space left on device
  ```

  The OS-level error is `ENOSPC`. All sessions are terminated and the server goes into crash recovery; free space before restarting it.
- Downstream, payments-pgbouncer-01.prod.internal and payments-pgbouncer-02.prod.internal can no longer open server connections. payments-api then logs `PAYAPI-E1042` because it cannot get a database connection from its pool in time, and returns errors to the edge.
- When the PANIC hits, every other connected session is cut off with SQLSTATE `57P02` (crash_shutdown, "terminating connection because of crash of another server process"). PgBouncer's server connections see this first, and payments-api sees failed queries.
- `57P01` (admin_shutdown, "terminating connection due to administrator command") means something else: an administrative shutdown of a *running* server, for example `systemctl stop` or `restart` during a planned failover. If you see `57P01` in this incident, someone shut the server down on purpose; it is not the disk.

## Step 1: buy space without touching WAL

Each payments-db VM carries a 10 GB ballast file for exactly this situation:

```
ls -lh /var/lib/postgresql/ballast
sudo rm /var/lib/postgresql/ballast
```

This is the only file on that volume you may delete. Recreate it after the incident (`sudo fallocate -l 10G /var/lib/postgresql/ballast`). If the volume can be grown online in the cloud console, request that in parallel; it takes about 15 minutes.

## Step 2: find what is holding WAL

Connect as the `postgres` user on payments-db-01:

```
sudo -u postgres psql
```

Check slots first:

```sql
SELECT slot_name, slot_type, active, wal_status,
       pg_size_pretty(pg_wal_lsn_diff(pg_current_wal_lsn(), restart_lsn)) AS retained
FROM pg_replication_slots
ORDER BY pg_wal_lsn_diff(pg_current_wal_lsn(), restart_lsn) DESC NULLS LAST;
```

- `active = false` with a large `retained` value is your answer.
- `wal_status` of `extended` means the slot is holding WAL beyond `max_wal_size`. `unreserved` means it is about to lose required WAL. `lost` means the consumer can no longer catch up from this slot.

Then check archiving:

```sql
SELECT archived_count, last_archived_wal, last_archived_time,
       failed_count, last_failed_wal, last_failed_time
FROM pg_stat_archiver;
```

If `last_failed_time` is recent and later than `last_archived_time`, archiving is broken. The Postgres log has the actual error from `archive_command` (permission denied, timeout, credentials).

Check the size on disk to confirm WAL is the culprit and not table bloat or a temp file explosion:

```
sudo du -sh /var/lib/postgresql/16/main/pg_wal
sudo du -sh /var/lib/postgresql/16/main/base
```

## Step 3: fix the holder

**Inactive physical slot for payments-db-02**

- Check the replica: is it up, and is it streaming? On payments-db-02, run `SELECT status, sender_host FROM pg_stat_wal_receiver;`.
- If the replica is just restarting or briefly partitioned, bringing it back is the best fix: it reconnects to the slot and the primary releases WAL as it catches up.
- If the replica cannot come back soon and the disk is about to fill, dropping the slot is acceptable **with the DBA lead's approval**. The replica must be re-cloned afterwards.

  ```sql
  SELECT pg_drop_replication_slot('payments_db_02');
  ```

**Inactive logical slot `cdc_payments`**

- Ask the reconciliation pipeline owner whether the connector can be resumed within the time you have.
- Dropping a logical slot means the pipeline must do a fresh snapshot. Same rule: DBA lead approves.

**Archiving failures**

- Fix the cause in the log (rotate the credential, restore network access). Archiving retries automatically. Watch `archived_count` climb and the `.ready` count in `pg_wal/archive_status` fall.
- Do **not** set `archive_command` to `/bin/true` to skip archiving. It frees disk, but it breaks point-in-time recovery until the next full base backup.

## Step 4: let Postgres remove the WAL

Once the holder is gone, run a checkpoint so old segments are removed now rather than at the next scheduled one:

```sql
CHECKPOINT;
```

Re-run the `du` on `pg_wal`. It should drop within a minute or two.

## Step 5: if the primary already crashed

If Postgres went down with the PANIC above:

1. Free space first (step 1), then start Postgres.
2. Start it: `sudo systemctl start postgresql@16-main`.
3. Watch the log until it reports that the system is ready to accept connections.
4. Then do steps 2 to 4 while the server is up.
5. Confirm payments-pgbouncer reconnects (`SHOW SERVERS;` on the admin console) and payments-api's `PAYAPI-E1042` rate drops to zero.

## Prevention

- `max_slot_wal_keep_size` is set to `200GB` on payments-db-01. A slot holding more than that is invalidated (`wal_status = lost`), and its consumer must be rebuilt. The value was chosen to ride out a day-long replica outage, but it is **above the free space on the 500 GB volume**, so today a stuck slot fills the disk first. Until the volume is grown or the cap is lowered below the free space, the 50 GB retained-WAL alert below is the real guard. Changing the cap needs only a reload:

  ```sql
  ALTER SYSTEM SET max_slot_wal_keep_size = '200GB';
  SELECT pg_reload_conf();
  ```

- Alert on `pg_replication_slots` retained bytes above 50 GB and on `pg_stat_archiver.failed_count` increasing.
- Recreate the ballast file after every incident.

## After the incident

Record in the ticket: which slot or archive failure held WAL, peak disk usage, whether the PANIC happened, how long payments-api was affected, and whether any slot was dropped and a replica re-cloned.
