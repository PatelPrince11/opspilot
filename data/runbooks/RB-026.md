# Did today's release do this?

For when auth-service misbehaves and something shipped today. Namespace `identity`, Deployment `auth-service`, 2 pods (auth-service-01.prod.internal and -02 in logs). Our rollouts keep the Deployment defaults: with 2 replicas that's one extra pod at a time and none removed early, so for a few minutes old and new versions serve side by side.

**Q1. Did the trouble begin during or soon after a rollout?**

```
kubectl -n identity rollout history deploy/auth-service
kubectl -n identity get rs -l app=auth-service -o wide
```

The newest ReplicaSet's AGE is when the rollout began.

- No rollout in the last few hours → not a deploy problem. Leave this page.
- Yes → Q2.

**Q2. Do the errors follow the new pods?**

```
kubectl -n identity get pods -l app=auth-service -L pod-template-hash
for p in $(kubectl -n identity get pods -l app=auth-service -o name); do
  echo "$p $(kubectl -n identity logs "$p" --since=20m | grep -c AUTH-E401X)"
done
```

- Errors sit on the new hash, or start the minute the first new pod turned Ready → the release. Go to Q3.
- Errors spread evenly over old and new pods → something they share. Check dependencies before blaming the code. For session errors: `redis-cli -h redis-sessions-02.prod.internal ROLE` shows which node is primary; an unchanged primary and no Redis write errors in auth-service's logs rule out a Redis switch.

**Q3. Did the release change anything stored or shared?**

Read the diff for: session or cache encodings, key names, database migrations, message formats, feature-flag defaults.

- Nothing of the kind → Q4.
- Yes → Q5.

**Q4. Roll back.**

```
kubectl -n identity rollout undo deploy/auth-service
kubectl -n identity rollout status deploy/auth-service
```

Errors should stop as old pods take over, about six minutes for both. Keep the bad ReplicaSet (don't delete it) so the squad can debug, and tell them.

**Q5. Data written by the new version: stop and think before rolling back.**

Every minute the new version runs, it writes things in its own format. A rollback means the old version meets those things.

- The old version can read what the new one wrote → Q4.
- It can't → both directions hurt. Staying forward breaks what the old version wrote; going back breaks what the new one wrote. Choose the smaller harm. Often the better move is a fast fix-forward that reads both formats, left running until the old data expires.
- Rolling back anyway: warn support that a second wave of errors is coming, from data written during the bad window.

**Q6. Done when** `AUTH-E401X` is back to its usual trickle on both pods for 30 minutes, and the ReplicaSet serving traffic is the one you meant.

## July 2026, for the record

A release changed how session values under the `sess:` prefix in redis-sessions were encoded. New pods couldn't decode sessions written by old pods, and the reverse. The rollout began at 14:05. At 14:08, as the first new pod became Ready, `AUTH-E401X` jumped and followed every request that reached a pod of the other version. By 14:11 both pods ran the new code, and every user holding an old-format session had been logged out once.

The page came at 14:14. Redis was checked first and was fine: same primary, no write errors. We rolled back at 14:20. From 14:23, as the first old-version pod returned, everyone who had logged in since 14:08 was logged out a second time; that wave faded by about 14:30.

No data was lost. The sessions were still in Redis; they just couldn't be read. On 2026-07-22 we shipped a version that reads both encodings. Looking back, the answer at Q5 was fix-forward.
