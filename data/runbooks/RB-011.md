# payments-pgbouncer saturation procedure

payments-pgbouncer is two VMs, payments-pgbouncer-01.prod.internal and payments-pgbouncer-02.prod.internal, each running PgBouncer 1.22 (systemd unit `pgbouncer`, config in `/etc/pgbouncer/pgbouncer.ini`) in front of payments-db-01. Each instance normally carries about half of payments-api's connections. Relevant settings, identical on both:

- `pool_mode = transaction`, `max_prepared_statements = 200`
- `default_pool_size = 40`: server connections per database/user pair
- `reserve_pool_size = 10`, `reserve_pool_timeout = 3`: up to 10 extra server connections, used only once a client has waited 3 seconds without being served
- `max_client_conn = 500`
- `query_wait_timeout = 10`: a client whose query waits 10 seconds for a server connection is disconnected

payments-api runs 4 pods with `pool_max_conns=40` each, so at most 160 client connections, about 80 per bouncer. In transaction mode a server connection is tied to a client only for the length of one transaction. Forty is plenty while transactions take milliseconds. Saturation means transactions got longer, or there are many more of them, and clients now queue inside PgBouncer.

How it reaches payments-api: a query that waits in PgBouncer keeps its pgx connection acquired for the whole wait. The 40-connection pool on each pod fills, new `Acquire` calls run into the 500 ms `DB_ACQUIRE_TIMEOUT` deadline, and payments-api logs `PAYAPI-E1042` and returns `503`. Latency on `/v1/payments/*` climbs first; E1042 follows.

## Procedure

**1. Look at the pools on both instances.**

```
psql -h payments-pgbouncer-01.prod.internal -p 6432 -U pgbouncer pgbouncer -c 'SHOW POOLS;'
psql -h payments-pgbouncer-02.prod.internal -p 6432 -U pgbouncer pgbouncer -c 'SHOW POOLS;'
```

Expected when healthy: `cl_waiting` 0, `maxwait` 0, `sv_active` well under 40, some `sv_idle`.

Saturated: `sv_active` at 40, then 50 once the reserve pool engages; `sv_idle` 0; `cl_waiting` above 0; `maxwait` in whole seconds. The reserve opens only after a client has waited `reserve_pool_timeout`, so `maxwait` past 3 s is normal here. With about 80 clients on 50 server connections, `cl_waiting` tops out near 30 per instance. A value well above that means more clients than usual are connected; go to step 2.

**2. Count clients per instance.**

```
psql -h payments-pgbouncer-01.prod.internal -p 6432 -U pgbouncer pgbouncer -c 'SHOW CLIENTS;' | grep -c payments
```

Expected: roughly 80 on each, never near `max_client_conn` (500). If one instance carries far more than half, the split is uneven: hand it to team-payments, and don't restart anything for it. If both are even and both are saturated, the cause is on the database side: continue.

**3. Rule out PgBouncer itself.** PgBouncer is a single process using one core.

```
ssh payments-pgbouncer-02.prod.internal 'top -b -n 1 -p $(pidof pgbouncer) | tail -2'
```

Expected: well below 100% CPU. If it is pinned at 100% of a core while `sv_idle` is still above 0, the bouncer is the bottleneck rather than the server pool. Escalate to team-payments infra; don't change pool sizes for this.

**4. Find what holds the server connections.** On payments-db-01.prod.internal:

```sql
SELECT left(query, 80) AS stmt,
       count(*) AS conns,
       round(avg(extract(epoch FROM now() - xact_start))::numeric, 2) AS avg_xact_s
FROM pg_stat_activity
WHERE usename = 'payments_app' AND state = 'active'
GROUP BY 1
ORDER BY conns DESC
LIMIT 10;
```

Expected in normal traffic: short statements, `avg_xact_s` well under 0.1. A group of statements averaging whole seconds, holding dozens of connections, is the culprit.

**5. Confirm Postgres still has room.**

```sql
SELECT count(*) FROM pg_stat_activity WHERE backend_type = 'client backend';
```

Expected: about 100 (both bouncers fully open) or less, against `max_connections = 200`. If so, the wait is entirely inside PgBouncer.

**6. Remove the load.** Stop whatever owns the long transactions: turn off the feature or job that issues them, then cancel the stragglers with `SELECT pg_cancel_backend(pid)`. Once they are gone, the queue drains within seconds.

Avoid these:
- Raising `pool_max_conns` on payments-api only adds clients to the same queue.
- Raising `default_pool_size` needs team-dba's agreement. Both instances together may open 2 × (pool + reserve) server connections, which must stay well inside payments-db's 200 (3 are reserved for superusers). After editing the ini, apply it with `RELOAD;` on the admin console.

**7. Verify.** `cl_waiting` 0 and `maxwait` 0 on both instances, `PAYAPI-E1042` back to zero, payment latency back to baseline.

## If waits pass 10 seconds

At `query_wait_timeout` PgBouncer disconnects the client. The client sees a FATAL `query_wait_timeout` error (SQLSTATE `08P01`) and the request fails.

## History

June 2025: a refunds export inside payments-api ran transactions of about 2 s each through the transaction pool, taking every server connection on both instances. `cl_waiting` sat at about 30 per instance with `maxwait` near 4 s. No `query_wait_timeout` errors appeared because waits stayed under 10 s, but pgx pools filled and `PAYAPI-E1042` followed. Disabling the export cleared it.
