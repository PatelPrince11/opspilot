# auth-db server certificate: questions and answers

Scope: auth-db-01.prod.internal (primary) and auth-db-02.prod.internal (replica), PostgreSQL 16 on VMs. Maintainer: team-dba.

**What is the arrangement?**

auth-service connects as `auth_app` with `sslmode=verify-full`. It checks that the server certificate chains to our internal CA, that it is within its validity dates, and that its name matches the host it dialled. The server's certificate and key are `server.crt` and `server.key` in `/etc/postgresql/16/main/`. A systemd timer, `pg-cert-renew.timer`, requests a new certificate from the internal CA 30 days before expiry and writes it over the old files.

**How does an expired certificate show up?**

auth-service logs connection errors containing `tls error` and `x509: certificate has expired or is not yet valid`, and logins fail with `503`. On the database side nothing looks wrong. Postgres raises no warning about its own certificate, and the connection count is normal or lower than usual.

**Why doesn't everything fail at the same moment?**

The certificate is checked when a connection is opened, never again afterwards. auth-service's pgx pool (`pool_max_conns=30` per pod) keeps connections for up to `pool_max_conn_lifetime=1h` and closes those idle longer than `pool_max_conn_idle_time=30m`; both are set in its `DATABASE_URL`. After expiry, connections that were already open carry on working, and every new one fails. Over the following hour the older connections age out, the pool can't replace them, and the failures climb. Errors that keep growing for tens of minutes, while the database looks healthy, are the signature.

**The file on disk is valid. Why is the server presenting an expired certificate?**

Postgres reads `ssl_cert_file` and `ssl_key_file` when it starts and when its configuration is reloaded. Writing new files changes nothing until one of those happens. Compare what the server sends with what is on disk:

```
openssl s_client -starttls postgres -connect auth-db-01.prod.internal:5432 </dev/null 2>/dev/null \
  | openssl x509 -noout -serial -enddate
sudo openssl x509 -in /etc/postgresql/16/main/server.crt -noout -serial -enddate
```

Different serials mean the server is still on the old certificate.

**How do we make it pick up the new one?**

Reload, don't restart:

```sql
SELECT pg_reload_conf();
```

`sudo systemctl reload postgresql@16-main` does the same. New connections get the new certificate, and existing sessions carry on undisturbed. A restart would also work, but it drops every session for no gain.

**Does the replica need the same?**

Yes. auth-db-02 has its own certificate and its own timer. Check and reload it the same way, even if nothing connects to it at the moment.

**What if the timer never got a new certificate at all?**

Then the files on disk are old too. `systemctl list-timers pg-cert-renew.timer` and `journalctl -u pg-cert-renew.service --since "-31d"` show the last runs and their errors. Ask the internal CA's owners for a certificate by hand, install both files owned by `postgres` with mode `0600` on the key, and reload.

**Can auth-service just stop verifying for now?**

No. `sslmode=require` keeps the encryption but accepts any certificate, including one from whoever sits in the path. That changes auth-service's security posture; it is not an incident fix.

**Has this happened?**

On 2025-04-08 the certificate on auth-db-01 expired at 09:00 UTC. The timer had written a valid replacement on 2025-03-09, but nothing told Postgres to load it. New connections from auth-service began failing at 09:00 while the older ones aged out over the next hour, and the error-rate alert paged at 09:38. At 09:47 `s_client` showed the old serial. `pg_reload_conf()` at 09:51 fixed it, and logins were normal again by 09:53. auth-db-02 was reloaded too.

Since 2025-04-09 the timer reloads Postgres after it writes the files.
