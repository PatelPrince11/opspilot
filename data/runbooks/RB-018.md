# Sessions and Redis failovers: what support and on-call ask us

Every logged-in session lives in redis-sessions: a Redis 7 primary and replica (redis-sessions-01.prod.internal, redis-sessions-02.prod.internal) managed by Sentinel. auth-service-01 and auth-service-02 write a session at login and look it up on every request. The questions below are the ones we keep answering.

**Users say they were suddenly logged out. Was it Redis?**

Look for `AUTH-E401X` in auth-service's logs. It means a session lookup failed and the user had to log in again. A spike that lines up with a redis-sessions primary change points at Redis. A steady trickle is normal: sessions expire.

**How can a failover log someone out if the data is replicated?**

Two ways. First, writes can fail during the switch. While the old primary is being demoted it becomes a replica, and a write sent to it gets `READONLY You can't write against a read only replica.` If a login's session write still fails with `READONLY` after the client's retries, auth-service logs the failed write and completes the login anyway, so the session is never stored. That user's next request looks up a session that doesn't exist, the lookup fails with `AUTH-E401X`, and they log in again. Second, an unplanned failover can lose writes. Replication is asynchronous, so writes the old primary acknowledged but hadn't yet sent to the replica are gone once the replica is promoted.

**How many users does that affect?**

Usually very few. The write-failure window lasts seconds, until the client learns the new primary, and only logins in that window on the affected instance lose their session. For unplanned failovers, the loss is bounded by how far the replica was behind at the moment of failure.

**Why would only one auth-service instance see `READONLY`?**

Each instance learns about the new primary on its own. One can switch a few seconds later than the other and send its writes to the demoted node in the meantime. If it's still seeing `READONLY` after a minute, something is wrong with that instance's connection to Sentinel: restart that pod (`kubectl -n identity rollout restart deploy/auth-service` restarts both, one at a time).

**Which node is the primary right now?**

```
redis-cli -h redis-sessions-02.prod.internal -p 26379 SENTINEL get-master-addr-by-name sessions
redis-cli -h redis-sessions-01.prod.internal INFO replication | head -5
```

The second command prints `role:master` or `role:slave` for that node.

**How far behind is the replica?**

On the primary, `INFO replication` lists each replica as `slave0:ip=…,port=…,state=online,offset=…,lag=…`. Compare its `offset` with the primary's `master_repl_offset`. The difference is the data an unplanned failover would lose.

**We need to patch the primary. How do we fail over on purpose?**

`redis-cli -h redis-sessions-02.prod.internal -p 26379 SENTINEL FAILOVER sessions`. This forces a failover without asking the other Sentinels to agree. Do it off-peak, watch `AUTH-E401X` for a couple of minutes, then patch the old primary once it has rejoined as a replica.

**Can we just restart Redis instead of failing over?**

Not as a substitute. A restart shorter than `down-after-milliseconds` (30 s) triggers no failover, because Sentinel never marks the primary down. It still drops every client connection, so every auth-service instance reconnects at once. What data the primary has when it comes back depends on its persistence settings. The Redis docs warn that a primary that restarts with an empty dataset makes its replicas copy that empty dataset. Check persistence before you restart, or fail over first.

team-platform runs redis-sessions; team-identity owns auth-service. Page team-platform for anything on the Redis side and keep us in the thread.

**Has this happened before?**

October 2025: a planned `SENTINEL FAILOVER sessions` before patching redis-sessions-01. For a few seconds, before auth-service-01 learned the new primary, its session writes hit the demoted node and failed with `READONLY`. The few users who logged in through that instance in that window were asked to log in again on their next request (`AUTH-E401X`). Nobody else was affected.
