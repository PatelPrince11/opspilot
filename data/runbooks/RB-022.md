# Cluster DNS is falling over

Pods never talk to internal-dns themselves. Each pod's resolver points at the cluster DNS Service: the `coredns` Deployment in `kube-system`, pods labelled `k8s-app=kube-dns`, 4 replicas. It answers cluster names on its own and forwards `prod.internal` to the two internal-dns VMs. When it's overloaded, everything in every namespace that needs a name suffers in the same minute.

## Is it this?

- [ ] Errors from several services in different namespaces, all starting together. Each runtime words it its own way:
  - Go (auth-service, payments-api, inventory-service): `lookup <name> on <cluster DNS IP>:53: ... i/o timeout`
  - Node (orders-api, notification-worker): `getaddrinfo EAI_AGAIN <name>`
  - Python (catalog-api, fraud-scorer): `[Errno -3] Temporary failure in name resolution`
- [ ] Names of every kind fail: `auth-db-01.prod.internal`, `catalog-db-01.prod.internal`, and short in-cluster Service names as well. One bad record would never touch cluster names.
- [ ] Requests on connections that were already open keep working. Failures land on new connections, so whichever service reconnects most shows it first.
- [ ] The datastore VMs don't notice anything: they ask internal-dns directly.

## Rule out internal-dns

- [ ] From any VM, ask both servers and read the status and timing:

  ```
  for s in 10.0.0.53 10.0.0.54; do dig @$s auth-db-01.prod.internal | grep -E 'status:|Query time'; done
  ```

  `NOERROR` in a few milliseconds from both means the authoritative side is fine. Don't touch it.

## Look at the cluster DNS pods

- [ ] `kubectl -n kube-system get pods -l k8s-app=kube-dns -o wide`: all Running and Ready? Restarts?
- [ ] `kubectl -n kube-system top pod -l k8s-app=kube-dns`: each pod near its CPU limit is the usual picture.
- [ ] Grafana, CoreDNS dashboard: requests per pod, the p99 of `coredns_dns_request_duration_seconds`, and `coredns_cache_hits_total` against `coredns_cache_misses_total`. Overload looks like p99 jumping from milliseconds to seconds while the request rate sits at or above its usual peak.
- [ ] One replica's log: `kubectl -n kube-system logs deploy/coredns --since=15m | tail -50`. Upstream errors naming 10.0.0.53 or 10.0.0.54 point back at internal-dns. None, and the pods are simply busy.

## Relieve it

- [ ] Add replicas: `kubectl -n kube-system scale deploy/coredns --replicas=<n>`. Doubling the replicas halves each one's share. New pods take queries once Ready, usually inside a minute.
- [ ] Pods pinned at their CPU limit and no room for more of them: raise the limit, leave the request.
- [ ] Don't restart the Deployment as a fix. Restarting overloaded pods removes capacity while they come back.
- [ ] Errors should fade within a couple of minutes of the new replicas being Ready. Apps retry lookups on their next request; nothing on the app side needs a restart.

## Afterwards

- [ ] Record the peak query rate and how many replicas it took. The replica count is fixed by hand, not autoscaled.
- [ ] Write a manual scale-up back into the Deployment's source, or the next rollout quietly undoes it.

## History

February 2025: the cluster had grown, the replica count hadn't. At the evening peak, about 19:50, both replicas sat at their CPU limit and lookups began timing out in auth-service, catalog-api and orders-api together. internal-dns answered at once when asked directly. The page came at 19:56. Scaling `coredns` from 2 to 4 replicas at 20:08 cleared it by 20:15, and it has run with 4 since.
