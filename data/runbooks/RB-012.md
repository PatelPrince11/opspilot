# SQLSTATE 53300 reference card

Applies to every PostgreSQL 16 server we run. Owner: team-dba.

## Definitions

**53300 (`too_many_connections`)**: the server refused a new session at login because its connection slots are used up. The error arrives at connect time, before any query runs. An application sees it as a failed connection attempt, not as a slow query.

**max_connections**: total session slots. Changing it requires a server restart.

**superuser_reserved_connections**: slots kept back for superusers. Ours is the default, 3.

**reserved_connections**: slots kept back for roles granted `pg_use_reserved_connections`. Ours is 0, the default.

**Usable slots for application roles** = `max_connections` − 3.

**Not counted**: WAL sender processes. Physical replicas and logical slots such as `cdc_payments` don't use `max_connections` slots.

**Counted**: every client backend, including admin, migration and psql sessions. Superuser sessions use the reserved 3 first.

## Which message, for which role

| Role connecting | Situation | Message (all SQLSTATE 53300) |
|---|---|---|
| Application role (`inventory_app`, `ledger_app`, `payments_app`, …) | fewer than 3 free slots left | `FATAL: remaining connection slots are reserved for roles with the SUPERUSER attribute` |
| Superuser (DBA) | every slot taken, reserved ones included | `FATAL: sorry, too many clients already` |
| Role without `pg_use_reserved_connections` | only when `reserved_connections > 0` | `remaining connection slots are reserved for roles with privileges of the "pg_use_reserved_connections" role` (never seen here, since we keep it at 0) |

So an application role at the limit almost always gets the "reserved for roles with the SUPERUSER attribute" text. "sorry, too many clients already" shows up mainly when a DBA tries to get in after the reserved slots are gone too.

## Connection budget per database

Pool sizes are per pod (or per bouncer for payments-db). Usable = `max_connections` − 3.

| Database | Who connects | Arithmetic | Usable |
|---|---|---|---|
| payments-db | payments-pgbouncer ×2, each `default_pool_size` 40 + reserve 10. payments-api's 4 × 40 = 160 client connections end at the bouncers, not here | 2 × (40 + 10) = 100 | 200 − 3 = 197 |
| ledger-db | ledger-service, Hikari `maximumPoolSize` 20, 2 pods | 2 × 20 = 40 | 197 |
| orders-db | orders-api, `pg` Pool `max` 25, 3 pods | 3 × 25 = 75 | 300 − 3 = 297 |
| auth-db | auth-service, pgxpool `pool_max_conns` 30, 2 pods | 2 × 30 = 60 | 197 |
| catalog-db | catalog-api, SQLAlchemy `pool_size` 10 + `max_overflow` 5, 2 pods | 2 × 15 = 30 | 100 − 3 = 97 |
| inventory-db | inventory-service, pool 20, 2 pods | 2 × 20 = 40 | 97 |

A rolling deploy briefly runs one extra pod (Deployment default `maxSurge` 25%, rounded up), so leave at least one pod's pool of headroom. A pool-size change multiplies by the pod count; the April 2026 row below is the example.

## Queries

Who holds the slots:

```sql
SELECT usename, application_name, client_addr, count(*)
FROM pg_stat_activity
WHERE backend_type = 'client backend'
GROUP BY 1, 2, 3
ORDER BY 4 DESC;
```

Current limits:

```sql
SHOW max_connections;
SHOW superuser_reserved_connections;
SHOW reserved_connections;
```

Ratio of used to total, for an alert or a quick look:

```sql
SELECT count(*) FILTER (WHERE backend_type = 'client backend') AS used,
       current_setting('max_connections')::int AS total
FROM pg_stat_activity;
```

## Levers, in order of preference

1. **Reduce the clients:** roll back the pool-size change, or scale back the deployment that grew.
2. **End idle sessions** that a client opened and forgot: `pg_terminate_backend(pid)` on rows with `state = 'idle'` and an old `state_change`. Check with the owning team first.
3. **Raise `max_connections`.** This is a restart, and each slot costs memory whether used or not. team-dba decides.

For payments-db, the server-side sessions belong to PgBouncer: also check the PgBouncer log on payments-pgbouncer-01/02.

## Recorded case

April 2026, inventory-db-01.prod.internal: an inventory-service release raised its pool from 20 to 80 per pod. 2 × 80 = 160 against 97 usable slots. Once 97 sessions were open, new `inventory_app` connections from inventory-service-01 and inventory-service-02 failed with 53300 and the "reserved for roles with the SUPERUSER attribute" message. The DBA on call could still log in through a reserved slot. Rolling back the release fixed it.
