# card-processor-proxy egress limiter

Reference card, team-payments.

## Terms

**Processor limit.** The card processor accepts at most 400 requests per second for our merchant account, all our traffic combined. Above that it answers 429, and the proxy logs `CPX-W429`.

**Local limiter.** Since 2026-07-09 the proxy also limits itself, so we stay under 400 without waiting for the processor to push back. Each proxy instance has its own token bucket. Settings live in ConfigMap `card-processor-proxy-config`:

- `CPX_LOCAL_RPS=180`: tokens per second, per instance
- `CPX_LOCAL_MAX_WAIT=2s`: the longest an attempt may queue for a token

**Queueing.** An attempt that finds no token joins a queue for up to 2 s. If a token frees up in time, it goes ahead late. If not, it is rejected when the 2 s run out. A rejected attempt logs `CPX-W430` and never reaches the processor.

**What takes a token.** Every attempt payments-api makes, retries included (`CPX_MAX_ATTEMPTS=3`).

**Budget.** 2 instances × 180 = 360 per second, 90% of 400. The split is fixed: an instance doesn't know when the other has gone.

## Placement

Proxy pods run only on the `egress` node pool: 2 nodes whose outbound addresses are on the processor's allowlist, selected by a nodeSelector and a taint toleration. Required anti-affinity puts one proxy per node. If one egress node is cordoned or down, the other already holds a proxy, so the replacement stays `Pending` until the node returns. Meanwhile one instance carries everything on a budget of 180.

## Reading the signals

| Seen | Meaning |
|---|---|
| `CPX-W430` only from card-processor-proxy-01.prod.internal, -02 silent | One instance gone; the survivor's 180 is the whole budget |
| `CPX-W430` from both | Genuine traffic above 360 |
| `CPX-W429` | The processor itself pushed back |
| `PAYAPI-E1107` | A payment used all 3 attempts |

`kubectl -n payments get pods -l app=card-processor-proxy -o wide` shows where each pod runs. The missing one is `Pending`, with a scheduling event naming anti-affinity or taints.

## Arithmetic for one instance

Take a steady-state arrival rate of 240 payment requests per second at payments-api, as measured. The extra load orders-api's own retries would add once payments start failing is ignored here.

Let *r* be the share of attempts rejected. A payment fails only if all three attempts are rejected, and every admitted attempt is one successful payment. So successes = 240 × (1 − *r*³) = 180, which gives *r*³ = 0.25 and *r* ≈ 0.63.

- **Attempts reaching the limiter:** 240 × (1 + 0.63 + 0.40) ≈ 487 per second, about twice the arrivals.
- **Failed payments:** 240 × 0.25 = 60 per second of `PAYAPI-E1107`, exactly the excess over budget.
- **Time:** waiting changes delay, not these counts. Under sustained overload the queue stays full, so admitted attempts have waited close to 2 s, and rejected ones the full 2 s. A failed payment spends about 6 s in the proxy across its three attempts.

The processor sees 180 per second throughout, far under 400, and answers normally.

## Levers

1. **Bring the missing instance back.** Usually fastest: find out why its node is unschedulable and fix that.
2. **One instance for a long time.** Raise `CPX_LOCAL_RPS` to 360 on the survivor, only while it runs alone, and set it back before the second starts; two at 360 could send 720, 1.8 × the processor's limit. The change needs a proxy restart. The Deployment uses maxSurge 0 and maxUnavailable 1, and the Pending replacement already uses up that one unavailable slot, so a rollout won't take the running pod down; it has to be deleted by hand, and the new one can only start on the same node after it's gone: a gap with no proxy at all.
3. **Not a lever:** more replicas. Anti-affinity allows one per egress node.

A shared budget across instances is proposed, not built.

## Recorded case, 2026-09-16

At 19:38 the egress node under proxy-02 was cordoned and drained for a kernel patch. At 19:40 proxy-02 was evicted, and its replacement went `Pending`. Payment requests were arriving at about 240 a second. From 19:41 proxy-01 logged `CPX-W430` and payments-api logged `PAYAPI-E1107`.

The page came at 19:48. At 19:55 the logs showed proxy-01 alone, no `CPX-W429`, and normal processor latency. Raising the limit would have cost a gap with no proxy, so we waited for the patch instead. The node could only be uncordoned after the patch and its reboot finished, which was at 20:18. Uncordoned at 20:20; proxy-02 Running at 20:22; `CPX-W430` stopped at 20:23.
