# Five-second checkouts: one lookup, eight questions

My notes from the third evening of the June 2026 checkout slowdown, tidied up. I've left the dead ends in, because that's where the time went.

## What you need to know first

orders-api is Node on a Debian-based image, so name resolution goes through glibc. Node's `dns.lookup`, which `pg` and the HTTP client use underneath, doesn't resolve anything on the event loop. It hands `getaddrinfo` to libuv's worker pool, which has 4 threads unless `UV_THREADPOOL_SIZE` says otherwise. The same 4 threads serve file system calls and some crypto. While a lookup hangs, it keeps one of them busy.

Our `pg` Pool (`max` 25 per pod) had `idleTimeoutMillis` at its default, 10 seconds. Checkout traffic arrives in bursts, so the pool closed idle connections between bursts and opened fresh ones at the start of the next. Every fresh connection begins with a lookup of `orders-db-01.prod.internal`.

## The notes

**17 June, 20:40.** Paged: `/checkout` p99 above 5 s, third evening in a row. p50 normal. It comes in bursts of a minute or two, then goes quiet.

**20:55.** Edge access logs for `/checkout`: status `200`, no response flag, `x-envoy-upstream-service-time` about equal to the total. The time is spent inside orders-api. The slow requests aren't spread out: they bunch just above 5 s, with a smaller group just above 10 s.

**21:10.** Not the heap. Memory per pod flat, no restarts, GC pause time normal, event-loop lag low. Whatever waits isn't holding the loop.

**21:15.** Durations stacked at multiples of five seconds smell like a timeout being hit and retried, not like slow work. The resolver's default timeout is 5 s. Time the lookups themselves.

**21:25.** Timed 200 lookups from inside a pod, through the same call the app makes:

```
kubectl -n commerce exec deploy/orders-api -- node -e '
const dns = require("dns"); let n = 0;
(function next() {
  const t = Date.now();
  dns.lookup("orders-db-01.prod.internal", () => {
    console.log(Date.now() - t);
    if (++n < 200) next();
  });
})();' | sort -n | tail -5
```

Most took 1 to 3 ms. Two took just over 5,000 ms. So: lookups, not queries.

**21:40.** Why would a lookup ever wait, with cluster DNS looking healthy on every dashboard? The pod's resolver config:

```
$ kubectl -n commerce exec deploy/orders-api -- cat /etc/resolv.conf
search commerce.svc.cluster.local svc.cluster.local cluster.local
nameserver <cluster DNS service IP>
options ndots:5
```

`ndots:5` means a name with fewer than five dots gets each search suffix appended first, and is asked as written only after those. Our database name has two dots. So one lookup is four names: three suffixed ones, each answered with NXDOMAIN (quickly), then the real one. glibc asks for an A and an AAAA record per name. **One lookup is 4 names × 2 record types = 8 queries over UDP.**

UDP doesn't promise delivery, and now and then a reply is lost. We never found out why on this cluster. When a reply is missing, the resolver waits out its 5 s timeout and asks that query again; the retry usually succeeds, so the lookup just comes back 5 s late. Two lost replies on two different queries of the same lookup, each recovered by its retry, cost about 10 s: still a `200`, just slow. That's the 10 s group. `getaddrinfo EAI_AGAIN` needs both tries of one query lost (the default is `attempts:2`), which is rarer still; a handful of those lines from those evenings were in the logs, for a name that resolved fine whenever I tried it.

Eight chances per lookup to lose a reply, not two. That's what lifted a rare event into the p99.

**21:50.** Why did whole bursts suffer, not only the requests that opened a connection? Four libuv threads. A burst opened a dozen connections at once; with two or three of those lookups sitting in a 5 s wait, every other lookup and file read queued for the remaining threads.

## What changed on 18 June

1. `dnsConfig` on the orders-api Deployment:

   ```yaml
   dnsConfig:
     options:
       - name: ndots
         value: "2"
   ```

   With `ndots:2`, a two-dot name is asked as written first, so `orders-db-01.prod.internal` resolves in 2 queries instead of 8: a quarter of the exposure. Names with no dot or one dot still walk the search list, so calls to other in-cluster services behave as before.

2. `idleTimeoutMillis: 60000` on the `pg` Pool, so a quiet minute between bursts doesn't throw connections away.

We didn't raise `UV_THREADPOOL_SIZE`. More threads would have hidden the stalls without making any lookup faster.

## Signs it's this again

- Slow requests stack near 5 s or 10 s; the edge says the time is inside the service.
- Heap and event loop healthy.
- A timed `dns.lookup` loop from a pod shows rare outliers around 5,000 ms.
- `getaddrinfo EAI_AGAIN` for a name that resolves when you try it by hand.
- The name has fewer dots than the pod's `ndots`.

No 5 s outliers on `/checkout` since 18 June. orders-api is the only Deployment that sets its own `ndots`; everything else keeps the cluster default of 5.
