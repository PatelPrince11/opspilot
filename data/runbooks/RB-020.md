# internal-dns: prod.internal names failing to resolve

Networking, team-platform. Read the first section even if you're in a hurry. Most wrong turns in DNS incidents come from not knowing which resolver answered.

## How a prod.internal name gets resolved

Every service finds its datastores by name: inventory-service connects to `inventory-db-01.prod.internal`, payments-api reaches payments-db through the payments-pgbouncer names, and so on. Those names live in one zone, `prod.internal`, and two servers are authoritative for it:

- internal-dns-01.prod.internal (10.0.0.53)
- internal-dns-02.prod.internal (10.0.0.54)

Both are VMs running CoreDNS (systemd unit `coredns`, config `/etc/coredns/Corefile`). Each serves the zone from a local zone file through CoreDNS's `file` plugin, which reloads the zone when its SOA serial changes. Records carry a 60 s TTL, and the SOA's negative-caching TTL is also 60 s. Each VM has its own copy of the file. The rollout tool updates them one after the other, so for a short time during a rollout the two can differ.

Clients reach the two servers by different paths:

- **VMs** list both servers in `/etc/resolv.conf`, internal-dns-01 first. glibc asks nameservers in the order listed. It moves to the second when the first doesn't answer, or when it answers over UDP with SERVFAIL, REFUSED or NOTIMP. An NXDOMAIN from the first server is a final answer, and glibc doesn't ask the second. So VMs follow internal-dns-01's answers unless it is down or failing. That holds only while the order stays as it is and `options rotate` isn't set.
- **Pods** ask the cluster's own CoreDNS. Its Corefile has a server block for `prod.internal` with `cache 30` and `forward . 10.0.0.53 10.0.0.54`. The `forward` plugin picks an upstream at random for each query it sends. The cache holds each answer, positive or negative, for at most 30 s, and every refresh can land on either server. If the two servers disagree, pods see whichever answer was cached last, and that changes from one cache period to the next.

## What the two codes mean here

**NXDOMAIN**: the server that answered says the name doesn't exist in the zone. This is an answer, not a failure, so CoreDNS's `forward` plugin keeps treating that server as healthy. Go reports it as `no such host`.

**SERVFAIL**: the server couldn't produce an answer at all. For a `prod.internal` name that usually means the zone isn't loaded on that server, or CoreDNS there is unhealthy. Go reports it as `server misbehaving`.

They need different fixes. NXDOMAIN almost always means the zone content is wrong. SERVFAIL means the server is wrong.

## Investigation

### Separate real failures from search-domain noise

A pod's `/etc/resolv.conf` uses `ndots:5` and search domains `<namespace>.svc.cluster.local svc.cluster.local cluster.local`. A name like `inventory-db-01.prod.internal` has only two dots, so the resolver first tries it with each search suffix, and each of those attempts gets NXDOMAIN from the cluster zone before the real name is asked. Cluster DNS always shows lots of NXDOMAIN. That is normal and tells you nothing. Only count NXDOMAIN for the `prod.internal` zone (the cluster CoreDNS metrics can be split by zone), or grep application logs for the exact name that failed.

### Find the exact name and who is affected

From the application side, search for `no such host` or `server misbehaving` with the hostname:

```
kubectl -n commerce logs deploy/inventory-service --since=30m \
  | grep -oE 'lookup [^ ]+ on [^ ]+: (no such host|server misbehaving)' \
  | sort | uniq -c | sort -rn | head
```

Note whether the failures are constant or come and go, and whether VM-based services (the datastores, the bouncers) have the same problem. Pods failing intermittently while VMs are fine is the fingerprint of the two servers disagreeing.

### Ask each server directly

From any VM, bypassing every cache:

```
dig @10.0.0.53 inventory-db-01.prod.internal +norecurse
dig @10.0.0.54 inventory-db-01.prod.internal +norecurse
dig @10.0.0.53 prod.internal SOA +short
dig @10.0.0.54 prod.internal SOA +short
```

Read the `status:` in each header and compare the SOA serials.

- Same serial and the same answer from both: the zone is consistent. If the answer is NXDOMAIN on both, the record really is missing. Check the most recent zone change.
- Different serials, and only one server returns NXDOMAIN: a partial rollout. The server with the newer serial has the content that broke.
- SERVFAIL from one server: look at that server's logs.

```
ssh internal-dns-02.prod.internal 'sudo journalctl -u coredns --since "-1h" | tail -50'
ssh internal-dns-02.prod.internal 'sudo systemctl status coredns --no-pager'
```

### Check the zone file itself

On each VM, compare the file you expect with the one on disk:

```
ssh internal-dns-01.prod.internal 'grep -n "inventory-db-01" /etc/coredns/zones/prod.internal.db'
ssh internal-dns-02.prod.internal 'grep -n "inventory-db-01" /etc/coredns/zones/prod.internal.db'
```

## Fixing it

**Record missing on one or both servers.** Restore the record in the zone source, bump the SOA serial, and roll the file to *both* servers. Confirm with the `dig` commands that both return the record with the same serial. A file with an unchanged serial isn't reloaded, so the bump is not optional.

**Rollout stuck halfway.** Either finish it (if the new content is right) or roll the old file back to the server that got it, again with a higher serial than either server has now.

**SERVFAIL from one server.** Restart CoreDNS there (`sudo systemctl restart coredns`) and recheck. If it fails to start, read the journal before doing anything else: a broken Corefile or zone file is the usual reason. While one server is broken, VMs move to the other when it times out or answers SERVFAIL or REFUSED. Pods will still send some queries to the broken one.

**Pods still failing after both servers agree.** Wait out the cluster cache. Negative answers are held for at most 30 s under the `cache 30` cap. If you can't wait, restart the cluster DNS: `kubectl -n kube-system rollout restart deploy/coredns`.

## Verification

- Both servers return the record with the same SOA serial.
- `no such host` for the name is gone from the application logs for 15 minutes.
- Cluster DNS NXDOMAIN for the `prod.internal` zone is back at its baseline.

## Background: the March 2026 incident

A zone-file rollout reached internal-dns-02 only (serial bumped, zone reloaded) and the new file was missing `inventory-db-01.prod.internal`. internal-dns-01 still had the old file. inventory-service-01 and inventory-service-02 logged `no such host` intermittently: each cluster DNS cache period got its answer from whichever server `forward` picked. The datastore VMs weren't affected because their resolv.conf lists internal-dns-01 first. Comparing the two SOA serials found it in minutes. The fix was to restore the record and roll the corrected file to both servers.
