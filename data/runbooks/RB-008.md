For any of our VMs (datastores mostly) where `/var` is on the root disk and logs ate it. Not for Postgres data volumes or Kafka log dirs, which have their own runbooks.

| You see | Do this |
|---|---|
| Disk alert on `/var` above 90%, e.g. on catalog-db-01.prod.internal | `df -h /var` then `sudo du -xh --max-depth=2 /var \| sort -h \| tail -15` to find the big directory |
| Writes fail with `No space left on device` / `ENOSPC` but `df -h` shows free space | Inodes ran out: `df -i /var`. Usually millions of tiny files in one spool or tmp directory |
| `/var/log/journal` is the biggest | `journalctl --disk-usage`, then `sudo journalctl --vacuum-size=500M`. Make it stick with `SystemMaxUse=500M` in `/etc/systemd/journald.conf` |
| One app log is huge and not rotated (`/var/log/opensearch/*.log` on search-cluster-02.prod.internal last time) | Check its logrotate file under `/etc/logrotate.d/`, run `sudo logrotate -f /etc/logrotate.d/<name>` |
| You deleted a big log but `df` didn't change | A process still has it open: `sudo lsof +L1`. Restart that process, or truncate it in place with `: > /proc/<pid>/fd/<fd>` |
| Old rotated logs piling up | `sudo find /var/log -name '*.gz' -mtime +14 -delete`, then check that `rotate N` is set in the logrotate config |
| Rotated logs keep reappearing as one giant file | The app keeps writing to the old file handle after rotation. Use `copytruncate` in its logrotate block, or have rotation send the app the signal it reopens logs on |
| Package cache large (`/var/cache/apt`) | `sudo apt-get clean` |
| kafka-02.prod.internal `/var` full from GC logs | Broker GC logs live in `/var/log/kafka`. Rotate them; don't touch `/data/kafka` from here |
| Back under 80% | Note the culprit in the ticket. If logrotate was missing, file a config-management fix so it doesn't return |
