# payments-api: pgx pool exhausted

payments-api is written in Go and talks to Postgres through a `pgxpool.Pool`, connecting via payments-pgbouncer to payments-db. Each request that needs the database calls `Acquire` on the pool. If every connection is checked out, the request waits. pgxpool has no acquire timeout of its own: `Acquire` waits until its context is done. So we wrap every `Acquire` in a context deadline from our own setting, `DB_ACQUIRE_TIMEOUT=500ms` in the `payments-api-config` ConfigMap. If the deadline passes before a connection frees up, we log `PAYAPI-E1042` and the handler returns `503`.

Pool settings live in the `DATABASE_URL` query string in the `payments-api-config` ConfigMap: `pool_max_conns=40`, `pool_min_conns=10`, `pool_max_conn_lifetime=30m`, `pool_max_conn_idle_time=5m`. With 4 pods (payments-api-01 to payments-api-04 in the logs) that's up to 160 client connections.

How we connect: payments-pgbouncer runs PgBouncer 1.22 in `pool_mode = transaction` with `max_prepared_statements = 200`, so pgx stays on its default exec mode (`cache_statement`, protocol-level prepared statements) and PgBouncer tracks the prepared statements per server connection. We don't use pgx's simple protocol. Don't add `default_query_exec_mode=simple_protocol` to the URL as an incident workaround; it changes how every query is sent and isn't a pool fix.

## Symptoms and what to do

| What you see | What it means | What we do |
|---|---|---|
| `PAYAPI-E1042` in logs, `503` on `/v1/payments/*` | Requests gave up waiting for a pool connection | Confirm with the pool metrics in the next row |
| `payments_db_pool_acquired_conns` flat at 40 on every pod; `payments_db_pool_acquire_wait_seconds` p99 near 0.5 | The pool is full and stays full | Find out who is holding connections (next rows) |
| Pool full on **one** pod only, e.g. payments-api-02.prod.internal | Something local to that pod: a stuck goroutine or a single slow batch | Take a goroutine dump from that pod, then delete the pod |
| `context deadline exceeded` wrapped around `Acquire` in stack traces | Same as E1042, logged by code paths that predate the error code | Treat as E1042 |
| Goroutine count climbing (Grafana "Go runtime" panel) | Requests piling up behind `Acquire` | Goroutine dump, see below |
| Acquired connections high, but payments-db shows most of our sessions `idle in transaction` | We open a transaction and then do something slow before committing, usually the card processor call | Find the code path in the dump; mitigate by restarting pods; fix: never call out while holding a tx |
| Acquired connections high, payments-db sessions mostly `active` on the same query | Slow query holding connections | Get the query from `pg_stat_activity`, page team-dba if it's a plan change |
| Pool full right after a deploy | New code path leaks: `rows.Close()` missing, or `tx.Rollback` skipped on an error branch | Roll back the deploy |
| Pool full after scaling payments-api **down** | Same traffic, fewer pods, fewer total connections | Scale back up |

## Goroutine dump

pprof is on port 6060, not exposed outside the pod.

```
kubectl -n payments port-forward pod/<pod> 6060:6060
curl -s 'http://localhost:6060/debug/pprof/goroutine?debug=1' > goroutines.txt
```

Look for many goroutines blocked in `pgxpool.(*Pool).Acquire`. Those are the waiters. The interesting ones are the goroutines that *hold* connections. Look for stacks inside a transaction helper that are blocked on something else (an HTTP call, a channel, a mutex).

## Sessions on the database side

On payments-db-01.prod.internal:

```sql
SELECT state, count(*), max(now() - state_change) AS oldest
FROM pg_stat_activity
WHERE usename = 'payments_app'
GROUP BY state;
```

To see what the long ones are running:

```sql
SELECT pid, state, now() - xact_start AS xact_age, left(query, 120)
FROM pg_stat_activity
WHERE usename = 'payments_app' AND state <> 'idle'
ORDER BY xact_age DESC NULLS LAST
LIMIT 20;
```

## Mitigation

- Restarting the pods (`kubectl -n payments rollout restart deploy/payments-api`) frees every held connection and usually restores service for a while, but take the goroutine dump first.
- Raising `pool_max_conns` hides the problem and moves the pressure to payments-pgbouncer and payments-db. Only do it if you've confirmed the pool is simply undersized for current traffic, and tell team-dba.
- If idle-in-transaction sessions are the cause and you can't restart quickly, team-dba can terminate them with `pg_terminate_backend(pid)`. The affected requests fail, and the connections come back.

## Done when

`PAYAPI-E1042` is back to zero, acquire wait p99 is under 50 ms, and acquired connections per pod are back to their usual 8 to 15.
