# Reservations timing out: walk the tree

Inventory squad. `INV-E220` = stock reservation timed out. orders-api shows it as `ORD-5003` on checkout. Start here and take the first branch that matches.

**A. Is `INV-E220` rising on inventory-service-01.prod.internal and inventory-service-02.prod.internal?**

- **Only one instance.** Look at that pod (CPU, restarts, GC) before the database. A single bad pod is not a query problem.
- **Both.** Go to B.

**B. Is inventory-db-01.prod.internal busy?**

`SELECT count(*) FILTER (WHERE state = 'active') AS active, count(*) AS total FROM pg_stat_activity WHERE usename = 'inventory_app';`

- **Active count near the pool total (40), and CPU high on inventory-db-01.** The database is doing too much work per query. Go to C.
- **Active count high, CPU low.** Sessions are waiting, not working. Go to D.
- **Few active sessions.** The database isn't the bottleneck. Check inventory-service's own pool wait and the network. Stop here and page the inventory squad lead.

**C. Which statement is expensive?**

```sql
SELECT calls, round(mean_exec_time::numeric, 1) AS mean_ms,
       round(total_exec_time::numeric / 1000) AS total_s,
       left(query, 90)
FROM pg_stat_statements
ORDER BY total_exec_time DESC
LIMIT 10;
```

- **Top entry touches `reservations` and `mean_ms` jumped since yesterday.** Run its plan with a real parameter:
  `EXPLAIN (ANALYZE, BUFFERS) <the statement with literal values>;`
  - **`Seq Scan on reservations`** with a filter on a column such as `expires_at` or `status`: a missing index.
    - Was there a release today that added this filter? If so, roll it back. That's the fastest fix.
    - Otherwise build the index without blocking writes:
      `CREATE INDEX CONCURRENTLY reservations_expires_at_idx ON reservations (expires_at);`
      It can't run inside a transaction block. If it fails, it leaves an `INVALID` index behind: drop it and rerun.
  - **Index scan, but row estimates off by orders of magnitude.** Stale statistics. Check `last_autoanalyze` in `pg_stat_user_tables` for `reservations`, then run `ANALYZE reservations;`.
  - **Plan looks fine, and the time is in I/O (high `shared read` in BUFFERS).** Cache churn from another workload. Find it in the same `pg_stat_statements` list.
- **Top entry is not on `reservations`.** Whoever owns that statement is starving the database. Find the owner and page them.

**D. What are the sessions waiting on?**

```sql
SELECT pid, wait_event_type, wait_event, pg_blocking_pids(pid) AS blocked_by, left(query, 60)
FROM pg_stat_activity
WHERE usename = 'inventory_app' AND state <> 'idle' AND wait_event_type IS NOT NULL;
```

- **`Lock`, many rows blocked by the same pid.** One transaction holds a row or table lock. Look at what that pid is running. If it's a stuck migration or a manual session, cancel it with `pg_cancel_backend(pid)` (team-dba approves `pg_terminate_backend`).
- **`IO` waits everywhere.** Storage latency on the VM. Page team-dba.

**E. Done when** `INV-E220` is back to zero for 15 minutes, `ORD-5003` stops on orders-api-01..03, and the expensive statement's `mean_ms` is back to its usual value.
