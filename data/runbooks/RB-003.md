# Search is slow or rejecting: which branch are you in?

Team catalog. Start at the top, follow the first branch that matches. Run cluster calls from a search-api pod or the bastion against `http://search-cluster-01.prod.internal:9200`.

**Start: is search-api returning `SRCH-E502` or HTTP `429`?**

- **Yes, rejections.** The cluster's search thread pool queue is full.
  - Check the pool on every node:
    `GET _cat/thread_pool/search?v&h=node_name,active,queue,rejected`
  - **Is `rejected` growing on all three nodes?**
    - **Yes.** Cluster-wide overload. Go to *Find the expensive query*.
    - **No, only one node (say search-cluster-03).** Hot shard or a bad node.
      - `GET _cat/shards?v&s=node` and look for a large shard of `products` that lives only on that node.
      - `GET _nodes/search-cluster-03/hot_threads`
      - If hot threads show merges or GC rather than search, page team-platform; this is not a query problem.
- **No rejections, just slow (edge shows `504` on `/search`).**
  - `GET _cat/nodes?v&h=name,cpu,load_1m,heap.percent`
  - **CPU above 90% on the nodes?**
    - **Yes.** Go to *Find the expensive query*.
    - **No.** Check search-api itself: its own CPU, its GC, and its connection pool to the cluster. Not a cluster problem.

**Find the expensive query**

- List running searches (detailed=true adds per-task detail):
  `GET _tasks?actions=*search*&detailed=true`
- Sort by `running_time_in_nanos`. **Anything running longer than 10 s?**
  - **Yes.** Read the description. Usual suspects:
    - leading wildcard (`*phone*`) on `title`
    - `terms` aggregation on `sku` with a huge `size`
    - deep paging (`from` in the thousands)
    - Cancel it: `POST _tasks/<node_id>:<task_id>/_cancel`
    - **Is it coming back?** Usually it's a crawler or an internal export hitting search-api-01.prod.internal or search-api-02.prod.internal in a loop. Find the caller in search-api's access log by request id, then block the client at the edge or turn on the `search.block_leading_wildcard` flag.
  - **No long tasks, but many medium ones.** That's volume, not one bad query. Check the request rate on search-api against yesterday's. If it's a traffic spike, don't add search-api replicas: more callers means more load on a cluster that's already full. Shed load with the edge rate limit for `/search` instead.

**Stop the bleeding while you investigate**

- Global safety net, dynamic:
  `PUT _cluster/settings {"persistent": {"search.default_search_timeout": "5s"}}`
- Revert to `-1` (no timeout) after the incident if you set it only for the incident.

**Before you close**

- Rejections back to zero (`rejected` stops increasing).
- `SRCH-E502` gone from search-api logs for 15 min.
- Note the query pattern in the ticket so search-api can validate it.
