# Pushing config to VMs

Maintained by the config-management maintainers in team-platform. Covers files the rollout tool pushes to VM-hosted daemons. Application services on Kubernetes roll out through their Deployments and are out of scope here.

## How the tool behaves

It pushes to one host first, the canary, then restarts or reloads the unit. It waits 60 s, checks that the unit is active, and runs a probe for that service. Only if both pass does it move to the next host, one at a time. On the first failure it stops and leaves the remaining hosts alone.

That gate applies only to units in its probe table:

| Unit | Probe |
|---|---|
| `kafka` | `kafka-broker-api-versions.sh --bootstrap-server <host>:9092` |
| `opensearch` | `curl -s http://<host>:9200/_cluster/health` |
| `redis-server` | `redis-cli -h <host> PING` |
| `redis-sentinel` | `redis-cli -h <host> -p 26379 PING` |
| `coredns` | `dig @<host> prod.internal SOA` |
| `postgresql@16-main` | `pg_isready -h <host>` |

A unit missing from the table still gets the older pacing: canary, a fixed 5-minute wait, the next host, and no check beyond the exit status of `systemctl restart`. Enrolling a unit means adding a row; ask us.

## Before the push

1. **Validate what can be validated.** For Postgres, place the file, then before any restart run `SELECT name, setting, error FROM pg_file_settings WHERE error IS NOT NULL;`. It lists every line the server couldn't apply, with the reason. A setting that only takes effect at restart also gets a message there, so read each row rather than treating any row as fatal. The other daemons have no dry run on our hosts, so read the diff against the daemon's documented types. A size written where an integer is expected is the classic mistake.
   *Why:* a daemon that rejects its config at startup stays down, and a restart is exactly when it reads the file.
2. **Choose the canary.** Pick the least-loaded host, and never a datastore's only host. Single-instance datastores get their own run, off-peak, with someone watching.
3. **Know what one host down costs.** Kafka here has replication factor 3 and `min.insync.replicas=2`. Losing one broker costs redundancy, not writes. Losing two stops every `acks=all` producer.

## During the push

4. **Watch the canary yourself**, not only the tool:
   `ssh <host> 'systemctl is-active <unit>; sudo journalctl -u <unit> --since "-5min" | tail -20'`
   *Why:* `systemctl restart` can report success for a process that dies seconds later. Our `kafka` unit is `Type=simple`, so systemd counts it as started as soon as the process launches.
5. **If the tool stops on a failure, don't rerun it.** A rerun starts at the canary again with the same bad file.

## When a daemon won't come back

6. **Stop the run** if the tool hasn't stopped itself, which is the case for any unit outside the table.
7. **Read why it refused:** `sudo journalctl -u <unit> -n 100`. A bad Kafka value ends startup with a line like:
   `org.apache.kafka.common.config.ConfigException: Invalid value 10MB for configuration message.max.bytes: Not a number of type INT`
8. **Revert by pushing the previous commit**, not by editing on the host; hand edits vanish at the next push. Push only to the failed hosts, then start the unit (`sudo systemctl start kafka`).
9. **Confirm recovery.** Run the unit's probe, then check health at the service level. For Kafka, this should print nothing once every replica is back in sync:
   `/opt/kafka/bin/kafka-topics.sh --bootstrap-server kafka-03.prod.internal:9092 --describe --under-replicated-partitions`
10. **Fix the change**, have it reviewed again, and push it as a new run.

## Why the gate exists: 2026-08-13

A change set `message.max.bytes=10MB` in `/opt/kafka/config/server.properties`, meaning to allow 10 MB messages. Kafka expects a plain number of bytes there. At the time, the tool used the older pacing for every unit.

- **10:12** kafka-01, the canary, restarted and exited seconds later on the `ConfigException`. No alert: the under-replicated alert needs 10 minutes.
- **10:17** After the fixed wait, kafka-02 got the same file and died the same way. With one broker left, no partition could keep two in-sync replicas, so every `acks=all` write failed. Clients logged lines such as `Connection to node 1 (kafka-01.prod.internal/10.0.33.11:9092) could not be established. Broker may not be available.`
- **10:19** Page on producer errors. **10:20** Run stopped; kafka-03 was due at 10:22.
- **10:25** Previous file pushed to kafka-01 and kafka-02, and both started. **10:27** Both up. **10:36** Every replica back in sync.

For those ten minutes without writes:

- ledger-service logged `LEDGER-E455` for each entry it couldn't publish, queued them, retried with backoff and had drained the queue by 10:28. Its CPU didn't move.
- Checkout didn't notice. orders-api writes order events to an outbox table in orders-db first, and the relay that publishes them fell behind, then caught up.
- notification-worker had nothing new to read, so its lag stayed flat.

The gate went live on 2026-08-20.
