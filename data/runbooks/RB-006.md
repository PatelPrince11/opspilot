fraud-scorer rss creep. ns `risk`. known cause: in-process feature cache grows without bound when redis-features is slow (`FRD-W118` in our logs, `PAYAPI-W0310` on the payments side).

```
# which pod is fattest
kubectl -n risk top pod -l app=fraud-scorer

# restarts + OOMKilled?
kubectl -n risk get pods -l app=fraud-scorer
kubectl -n risk describe pod <pod> | grep -A3 'Last State'

# is redis-features slow? (feeds the cache growth)
redis-cli -h redis-features-01.prod.internal --latency

# FRD-W118 rate (deploy/ picks one pod; repeat per pod)
kubectl -n risk logs deploy/fraud-scorer --since=15m | grep -c FRD-W118

# what each worker is doing right now (pod needs SYS_PTRACE; debug image has it)
# pid 1 is the gunicorn master; dump each worker separately
kubectl -n risk exec <pod> -- pgrep -P 1
kubectl -n risk exec <pod> -- py-spy dump --pid <worker_pid>
# or a live view across master + workers (needs a tty)
kubectl -n risk exec -it <pod> -- py-spy top --pid 1 --subprocesses

# allocation diff: tracemalloc is on in the debug build
kubectl -n risk exec <pod> -- curl -s 'http://localhost:8080/debug/tracemalloc?top=20'

# stopgap: workers recycle every N requests (already set: --max-requests 5000 --max-requests-jitter 500)
# if growth outruns that, restart
kubectl -n risk rollout restart deploy/fraud-scorer
```

seen on fraud-scorer-01.prod.internal and fraud-scorer-02.prod.internal, mostly when redis-features latency spikes (big key scans, BGSAVE on the single node).
